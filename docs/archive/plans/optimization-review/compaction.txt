SUMMARY: The compaction core is mostly sound. Ledger work runs under the lock, loop stamps discard work from ended loops, chunks are matched by content hash, the floor catches a failed Observer, and 
I found no off-by-one or unawaited-promise bug in the handler. The weak point is the promise of no model call on the compaction path, which fails in two places the stats measure. First, when one row 
of the live context differs from the history anywhere under the watermark, all background notes are thrown away. Second, workflow subagents are never observed in the background at all. Together these 
make 106 of 162 recent subagent compactions and several auto ones wait 20–74 s on the Observer. Nothing puts a time limit on that wait, and a compaction also repeats Observer calls that background 
jobs already have in flight. (I could not run /improve-codebase-architecture: the skill blocks model invocation, so the user has to run it. The one structural fix inside this dimension, a single 
shared function for finding unobserved row ranges, is folded into D4.)

=== D4 [medium] Compaction repeats Observer calls on rows that background jobs are already observing, and ignores MAX_PARALLEL

... $.clock.after(0, () => void runJob($, job, v))`: no promise is kept, so there is nothing to await. hooks/register.ts:1700-1701: every landing calls `schedule` for waiting loops, and nothing marks

235k chunk tokens. That is an upper bound, because stats do not record which loop a call belongs to. Each duplicate costs a full call of about 18 s, where waiting for the call already running would 
take only its remaining time. During a compaction up to 4 background plus 7 on-the-spot pi processes run at once. commit then drops the duplicate (register.ts:1461), so there is no double counting, 
only waste.
SUGGESTION: Keep each Job's promise, and have one `gapsOf(ledger, v, running, limit)` used by both schedule and session.compact, so both skip the same covered ranges. At compaction, treat the loop's

ESSENCE: The same rows are observed once, by the job that started first. The cut still falls at the committed watermark, and background observation is unchanged.
PRIOR: None found. TODO.md:37-45 covers chunks run side by side not seeing each other's constraints, not calls repeated on the same rows.
VERDICT: partly / low

commit then drops the duplicate (1461). My overlap recount (21 of 129 blocking compactions, 31 calls in flight and 40 started) matches the reviewer's upper bound. It cannot be tied to a loop, and

critical path short. Capping it would add latency. (2) Compaction observes on the spot only when more than RAW_MAX_TOKENS = 40k tokens (register.ts:46) sit past the watermark. With the background 
healthy that seldom happens, so most overlaps follow C1 restarts or loops the background has fallen far behind. Fixing C1 removes much of this. (3) Background jobs in flight that land after the 
install are discarded anyway by `locate` (1678-1679). So awaiting them within a deadline is the useful part of the suggestion. The shared `gapsOf` and the compacting flag add state for a small gain.
CORRECTION: Keep the core: compaction can re-observe rows that a background job for the same loop already has in flight. Drop 'ignores MAX_PARALLEL', which is by design. Size it as a secondary waste, 
mostly downstream of C1 and loops the background has fallen behind on. The minimal fix: at compaction, treat the loop's in-flight ranges as covered and await those jobs' promises within the D3 
deadline.
