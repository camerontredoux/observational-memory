# qmd (Query Markdown Documents): how it works and where it could fit

> **Version read.** `tobi/qmd` at commit `04e4dbd8245c527a88f1a8f0bda547aef9ca81fb` (2026-09-09, `git describe` = `v2.8.3-24-g04e4dbd`). `package.json` says `@tobilu/qmd` 2.8.3 (`package.json:2-3`). The latest release is `v2.8.3`, 2026-08-16 (`CHANGELOG.md:17`). Every `qmd:` path below is relative to that commit: `https://github.com/tobi/qmd/blob/04e4dbd8245c527a88f1a8f0bda547aef9ca81fb/<path>`.
>
> **Sources.** Primary only: the repo's source, README, `package.json`, `CHANGELOG.md`, tests, the GitHub API, and GitHub issues. No blog posts. Sections 1–7 and 9 come from reading the code; qmd was not run for them. Model download sizes come from HTTP `HEAD` requests to the Hugging Face files the code names. Section 8 gives the results of a hands-on test on our own data.

## 1. Bottom line

- qmd is a local search engine for a folder of text files. It stores each file in SQLite, indexes it with FTS5 (BM25), and optionally embeds ~900-token chunks into sqlite-vec (`qmd:src/store.ts:114-118,1026-1031,1495`).
- It has three search modes. `search` is BM25 only. `vsearch` is vectors only. `query` is hybrid: query expansion, BM25 plus vectors, RRF fusion, and LLM reranking (`qmd:README.md:841-862`).
- `search` needs no model. The code says so in its own error text: "'qmd search' works without any model downloads" (`qmd:src/llm.ts:498`). `vsearch` needs one model. `query` needs three.
- The three default models total about 2.25 GB to download: 334 MB embedder, 639 MB reranker, 1.28 GB query-expansion model (Hugging Face `HEAD`, section 4.2).
- The unit of ranking is the **file**. BM25 runs over whole documents (`qmd:src/store.ts:4107-4126`). Hybrid results are deduplicated by file (`qmd:src/store.ts:4657-4700`). qmd cannot rank lines or blocks inside one file.
- Exact compound identifiers are handled well. A query term with a separator, such as `shard-101`, becomes an FTS5 phrase `"shard 101"`. A document that holds only `101` does not match it (`qmd:src/store.ts:3996-4006`). A bare term, such as `101`, becomes a prefix match `"101"*`.
- Interfaces are a CLI, an MCP server (stdio or HTTP), and a Node/Bun SDK (`qmd:README.md:89-459`). Our plugin cannot import the SDK: hook modules run with "no DOM, no Node" (`.claude/types/claude-code.d.ts:17-18`). The plugin can reach qmd only through `$.process.run` or `$.mcp.call`.
- License: MIT. Maturity: very active, one main maintainer, 17 tags and 28 changelog entries since 2025-12-07 (section 6).
- **Fit.** (a) As a backend for `om_recall` in one session: no. It ranks files, not blocks, and its `search` mode is the BM25 we already measured and rejected. (b) As a cross-session long-term tier: plausible, as an **optional** reader of markdown files that the plugin writes. The plugin must not depend on qmd. (c) The cheapest fit is to write promoted originals as plain markdown into a known directory. A user who runs qmd then indexes that directory with no plugin code for qmd at all.
- **Measured (section 8).** `om_recall` equals or beats qmd on identifiers and keywords, at about 10 ms. qmd's vector search closes `om_recall`'s real gap: questions worded differently from the transcript (13 of 22 in the top 5, against 4 of 22). Hybrid mode and reranking added nothing over plain vector search, at 50 to 1,000 times the latency.

## 2. How it works

### 2.1 Indexing pipeline

- A **collection** is a directory plus a glob mask. The default mask is `**/*.md` (`qmd:src/store.ts:57`, `qmd:README.md:622-632`). Collections live in YAML at `~/.config/qmd/index.yml`, not in SQLite (`qmd:README.md:715-777`, `qmd:src/store.ts:1200-1202`).
- `qmd update` walks each collection with `fast-glob`. It does not follow symlinks. It skips dot-files and files under dot-directories (`qmd:src/store.ts:1635-1646`).
- It reads each file whole as UTF-8 (`qmd:src/store.ts:1675`). It skips an empty file (`qmd:src/store.ts:1686-1689`). It skips a file it cannot read and continues (`qmd:src/store.ts:1676-1684`).
- It hashes the content. An unchanged hash is skipped. A changed hash stores the new content and updates the row (`qmd:src/store.ts:1691-1726`).
- Files that are gone are marked inactive, not deleted. Orphaned content is then removed (`qmd:src/store.ts:1734-1746`).
- The title comes from the first `#`/`##` heading for `.md`, from `#+TITLE` for `.org`, else from the file name (`qmd:src/store.ts:2908-2935`).
- Storage is one SQLite file, by default `~/.cache/qmd/index.sqlite` (`qmd:README.md:1209-1211`). A named index (`--index <name>`) uses its own file (`qmd:README.md:1061-1062`).
- Tables (`qmd:src/store.ts:1204-1256`):
  - `content`: content-addressed text, keyed by hash.
  - `documents`: collection, path, title, hash, times, `active` flag.
  - `documents_fts`: FTS5 over `filepath, title, body`, tokenizer `porter unicode61` (`qmd:src/store.ts:1026-1031`).
  - `content_vectors` and `vectors_vec`: chunk rows and a sqlite-vec `vec0` table with cosine distance (`qmd:src/store.ts:1247-1256,1495`).
  - `llm_cache`: cached query expansions and rerank scores.
- **Embedding is a separate step** (`qmd embed`) (`qmd:README.md:659-676`). Chunks are ~900 tokens with 15% overlap (`qmd:src/store.ts:114-118`). The chunker scores markdown break points (headings, code fences, blank lines) and does not cut inside a code fence (`qmd:README.md:1267-1307`). Tree-sitter chunking for code files is opt-in with `--chunk-strategy auto` (`qmd:README.md:1297-1309`).
- Only content hashes with no current vectors are embedded (`qmd:src/store.ts:1907-1930`). Vectors are keyed by content hash, so a file whose text changes gets a new hash. Its chunks are then embedded again. This is our reading of the code; section 8 did not measure it.
- Changing the embedding model requires `qmd embed -f`, which re-embeds everything (`qmd:README.md:581-599`).

### 2.2 Query pipeline

- **BM25** (`searchFTS`). FTS5 `bm25()` with column weights filepath 1.5, title 4.0, body 1.0 (`qmd:src/store.ts:4107-4113`). The score is mapped to `|x| / (1 + |x|)`, range 0 to 1 (`qmd:src/store.ts:4154`). With a collection or metadata filter it fetches `limit * 10` candidates, then filters (`qmd:src/store.ts:4100-4105`).
- **Vector search** (`searchVec`). Embeds the query and runs a nearest-neighbour query on `vectors_vec` (`qmd:src/store.ts:4236`).
- **Hybrid** (`hybridQuery`, `qmd:src/store.ts:5538` onward):
  1. BM25 probe. If the top score is at least 0.85 and leads the second by at least 0.15, query expansion is skipped (`qmd:src/store.ts:426-427,5560-5580`).
  2. Query expansion by the local 1.7B model. It returns typed sub-queries: `lex` go to FTS, `vec`/`hyde` go to vector search. Results are cached (`qmd:README.md:532-546`).
  3. RRF with `k = 60`. The original query gets double weight. A #1 in any list gets +0.05; #2-3 get +0.02 (`qmd:src/store.ts:4657-4700`).
  4. Rerank the top 40 candidates (`qmd:src/store.ts:430`). The reranker scores the best chunk of each document, not the whole body (`qmd:README.md:1311-1347`).
  5. Position-aware blend. RRF rank 1-3 keeps 75% retrieval weight, 4-10 keeps 60%, 11+ keeps 40% (`qmd:src/store.ts:5781-5788`). The README says this "prevents the reranker from destroying high-confidence retrieval results" (`qmd:README.md:547`).
- `structuredSearch` takes caller-typed sub-queries (`lex`/`vec`/`hyde`) and skips the expansion model (`qmd:src/store.ts:5960` onward). The MCP `query` tool and HTTP `/query` use it (section 3.2).

### 2.3 Which steps need a model

| Step | Model | Needed by |
|---|---|---|
| BM25 (`search`) | none | — |
| Embedding (`embed`, `vsearch`, vector half of `query`) | `embeddinggemma-300M-Q8_0` | `vsearch`, `query` |
| Query expansion | `qmd-query-expansion-1.7B-q4_k_m` (Qwen3-1.7B fine-tune, `qmd:finetune/README.md:5`) | `query` with a plain string; skipped on a strong BM25 signal or with typed sub-queries |
| Reranking | `qwen3-reranker-0.6b-q8_0` | `query`; skipped with `--no-rerank` or MCP `rerank: false` (`qmd:README.md:880`) |

Model URIs: `qmd:src/llm.ts:282-285`. Cache directory: `~/.cache/qmd/models/` (`qmd:src/llm.ts:324-327`). A test checks that `node-llama-cpp` is only imported dynamically, so lightweight commands do not load it (`qmd:test/cli-lazy-llm-import.test.ts:6-13`).

### 2.4 README drift

The README is behind the code in places. Trust the code.

- README says the top **30** candidates are reranked (`qmd:README.md:537,1334`). The code uses **40** (`qmd:src/store.ts:430`), and the flag table also says 40 (`qmd:README.md:881`).
- README says BM25 is converted with `Math.abs(score)`, range 0 to ~25 (`qmd:README.md:528`). The code uses `|x| / (1 + |x|)` (`qmd:src/store.ts:4154`).
- README's schema lists `collections` and `path_contexts` tables (`qmd:README.md:1215-1223`). The code drops both (`qmd:src/store.ts:1200-1202`).

## 3. Interfaces

### 3.1 CLI

- Search: `qmd search`, `qmd vsearch` (alias `vector-search`), `qmd query` (alias `deep-search`) (`qmd:README.md:841-865`).
- Search flags: `-n`, `-c/--collection`, `--all`, `--min-score`, `--full`, `--line-numbers`, `--explain`, `--filter <json>`, `--index <name>`, `--intent`, `--no-rerank`, `-C/--candidate-limit`, `--full-path` (`qmd:README.md:867-886`).
- Output formats: `--format cli|json|csv|md|xml|files` (`qmd:README.md:888-890`). `--json` and `--files` are the documented agent formats (`qmd:README.md:74-87`).
- Retrieval: `qmd get <file>[:from[:count]]`, by path or by 6-character docid; line-numbered by default. `qmd multi-get` takes a glob or list, with `--max-bytes` (default 64 KB) (`qmd:README.md:892-901,1108-1134`).
- Collections: `qmd collection add|remove|rename|list|show|include|exclude|update-cmd` (`qmd:README.md:622-657`). Contexts: `qmd context add|list|rm` (`qmd:README.md:692-713`).
- Maintenance: `qmd status`, `qmd update`, `qmd doctor`, `qmd init` (project-local index), `qmd cleanup` (`qmd:README.md:1092-1139`).
- A collection can run a shell `update` command before each `qmd update`. A non-zero exit aborts the whole update. Project-local configs need trust before such commands run (`qmd:README.md:779-839`).
- Benchmarks: `qmd bench` with JSON fixtures, backends `bm25|vector|hybrid|full`, precision/recall/MRR/F1 (`qmd:README.md:1140-1207`).

### 3.2 MCP server

- `qmd mcp` runs over stdio. `qmd mcp --http [--port] [--daemon]` runs over HTTP on `localhost:8181`; `qmd mcp stop` stops the daemon (`qmd:README.md:132-144`).
- Tools: `query`, `get`, `multi_get`, `status` (`qmd:src/mcp/server.ts:268-269,441,518,591`). Resource: `qmd://{+path}` (`qmd:src/mcp/server.ts:213-222`).
- `query` takes exactly one of a plain `query` string or typed `searches` (`lex`/`vec`/`hyde`), plus `limit` (default 10), `minScore`, `candidateLimit`, `collections`, `filter`, `intent`, and `rerank` (default true) (`qmd:src/mcp/server.ts:340-362`).
- `query` returns a text summary and `structuredContent.results`, each with `docid`, `score`, and a line-numbered `snippet` (`qmd:src/mcp/server.ts:405-432`).
- HTTP also serves `GET /health` and `POST /query` / `POST /search`, which take typed `searches` (`qmd:src/mcp/server.ts:1009,1019-1047`). Origin and Host checks are on by default; `QMD_ALLOWED_ORIGINS` and `QMD_ALLOWED_HOSTS` change them (`qmd:src/mcp/server.ts:1177-1179`).

### 3.3 SDK

- `createStore({ dbPath, config })` returns a `QMDStore` (`qmd:src/index.ts:261,385`).
- Methods include `search` (hybrid), `searchLex`, `searchVector`, `get`, `multiGet`, collection and context management, `update`, `embed`, `status`, and `close` (`qmd:src/index.ts:261-330,431-595`; `qmd:README.md:209-459`).
- `update` returns `{ collections, indexed, updated, unchanged, removed, needsEmbedding }` (`qmd:README.md:391-401`).
- The SDK needs Node or Bun. Our hook modules have neither (`.claude/types/claude-code.d.ts:17-18`).

### 3.4 Non-markdown files

- Any glob works, so `.jsonl` or `.txt` can be indexed (`qmd:README.md:628-632`). The indexer reads any file as UTF-8 text (`qmd:src/store.ts:1675`).
- Only `.md` and `.org` get a real title. Other files are titled by file name (`qmd:src/store.ts:2908-2935`).
- The markdown chunker still runs on them. A JSONL transcript has no headings, so chunks break on line breaks (score 1) (`qmd:README.md:1275-1287`).
- A whole transcript would be **one document**. A search hit names the file and a snippet. It does not rank the rows inside it.

### 3.5 Deleting and re-indexing

- Delete a file, then run `qmd update`: the row is marked inactive (`qmd:src/store.ts:1734-1742`). `qmd cleanup` removes inactive rows and caches (`qmd:README.md:1136-1138`).
- `qmd collection remove <name>` drops a collection (`qmd:README.md:637-638`).
- Re-indexing reads and hashes every file in the collection each time (`qmd:src/store.ts:1656-1732`). Unchanged files cost a read and a hash. Only changed content is written and, after `qmd embed`, embedded.

## 4. Runtime

### 4.1 Requirements

- Node.js >= 22 or Bun >= 1.0 (`qmd:README.md:560-563`). On macOS, Homebrew SQLite for extension loading (`qmd:README.md:564-567`).
- Install: `npm install -g @tobilu/qmd` or `bun install -g @tobilu/qmd` (`qmd:README.md:31-34`).
- Native dependencies: `better-sqlite3`, `sqlite-vec` 0.1.9 (per-platform optional packages), `node-llama-cpp` 3.20.0, four tree-sitter grammars (`qmd:package.json:59-80`).
- `node-llama-cpp` picks Metal, CUDA, Vulkan, or CPU. It prefers prebuilt bindings. It builds llama.cpp from source when no prebuilt fits and the install directory is writable (`qmd:src/llm.ts:1016-1040`). `QMD_FORCE_CPU` and `QMD_LLAMA_GPU` override this (`qmd:README.md:1225-1234`).

### 4.2 Models: size and cold start

| Model | README size | Measured `content-length` |
|---|---|---|
| `embeddinggemma-300M-Q8_0.gguf` | ~300 MB | 333,590,944 B |
| `qwen3-reranker-0.6b-q8_0.gguf` | ~640 MB | 639,153,184 B |
| `qmd-query-expansion-1.7B-q4_k_m.gguf` | ~1.1 GB | 1,282,438,912 B |

README sizes: `qmd:README.md:569-579`. Measured by `curl -I` on the `hf:` URIs in `qmd:src/llm.ts:282-285`, 2026-09-26.

- Models load on first use. They stay loaded for 5 minutes of inactivity by default (`qmd:src/llm.ts:658-659`).
- The reranker context defaults to 4096 tokens; `QMD_RERANK_CONTEXT_SIZE` overrides it (`qmd:src/llm.ts:1336-1344`).
- Parallelism is sized from free VRAM or CPU cores (`qmd:src/llm.ts:1173-1180`).
- Each CLI call is a new process, so it pays model load each time. The HTTP daemon keeps models warm. The changelog reports warm query latency down "from ~16s to ~10s" with the daemon (`qmd:CHANGELOG.md:1039-1046`, v0.9.0).
- The changelog also reports up to 2.7x faster reranking from parallel contexts (`qmd:CHANGELOG.md:1006,1017`, v1.0.0). It reports type-routed expansion cutting a query from 10.0 to 6.0 backend calls and 1278 ms to 549 ms (`qmd:CHANGELOG.md:1049`).
- These numbers come from the maintainers' machines. The repo publishes no indexing throughput figure.

### 4.3 Memory: open issues

- [#942](https://github.com/tobi/qmd/issues/942): concurrent `query` calls each load models; about 4.5 GB peak RSS per concurrent query on a 16 GB CPU-only host.
- [#962](https://github.com/tobi/qmd/issues/962): search scalability and bounded memory; the issue reports 35-60x faster queries and about 9x lower peak memory from bounded hydration.
- [#709](https://github.com/tobi/qmd/issues/709): practicality on a CPU-only VPS.
- [#977](https://github.com/tobi/qmd/issues/977): a missing or corrupt model can hang.
- [#971](https://github.com/tobi/qmd/issues/971): MCP stdout races.
- [#921](https://github.com/tobi/qmd/issues/921): duplicate query-expansion cache entries.

## 5. Exact identifiers

- The FTS tokenizer is `porter unicode61` (`qmd:src/store.ts:1026-1031`). It splits at every character that is not a letter or digit. Porter stems English words, so `decided` also matches `decide`.
- Query parsing (`buildFTS5Query`, `qmd:src/store.ts:3946-4031`):
  - A term with a separator (`shard-101`, `DEC-0054`, `src/lib/i18n.ts`, `@tobilu/qmd`) is split the same way the tokenizer split the document. It becomes an FTS5 phrase of its parts: `"shard 101"`. The parts must be adjacent and in order (`qmd:src/store.ts:3904-3917,3996-4006`).
  - A term with no separator becomes a prefix match: `101` → `"101"*` (`qmd:src/store.ts:4006`).
  - Underscore and apostrophe are kept in the query term. FTS5 applies the same tokenizer to the quoted term, so `apply_secrets` splits the same way on both sides (`qmd:src/store.ts:3893-3902`).
  - Quoted phrases are exact phrases. `-term` is negation. All positive terms are ANDed (`qmd:src/store.ts:4016-4030`).
- **`shard-101` versus `101`.** The query `shard-101` needs `shard` then `101` adjacent. A document that holds only `101` does not match at all. This fixes the failure we saw with plain BM25. The test file `qmd:test/store-fts-separator-queries.test.ts` covers these cases (lines 138-195).
- **Limits of this handling.**
  - It is separator-blind. `shard-101` also matches `shard 101`, `shard/101`, and `shard.101`.
  - A bare `101` also matches `1010` and `101st` (prefix match).
  - A SHA is one alphanumeric token. A short SHA prefix matches the full SHA through the prefix rule. We did not check how the porter stemmer treats hex tokens that end in letters.
  - Ranking among matching documents is still BM25 over the whole file. A long file with many hits can outrank a short file with one exact hit.
- **In hybrid mode**, an exact BM25 hit can still move down. The strong-signal rule skips expansion when BM25 is decisive (`qmd:src/store.ts:5560-5580`). The #1 bonus and 75% retrieval weight for ranks 1-3 protect the top (`qmd:src/store.ts:4690-4696,5781-5788`). A hit at RRF rank 4 or lower gets more reranker weight.

Compare `om_recall`: it matches within blocks of one transcript and ranks blocks that hold a term whole before blocks that hold its parts (`hooks/recall.ts:565-569`). On 90 real queries it put the needed block first 75 times, BM25 70 times (`docs/bench/2026-09-25-bm25.md:52,120`). qmd's lex mode would be one more BM25 variant with better compound handling. It works at file level, not block level.

## 7. Where qmd could fit in observational-memory

Constraints from our side:

- Compaction must be fast, non-blocking, cheap, a real reduction, and faithful. "The trade for speed and accuracy is storage" (`docs/plans/compaction-goals.md:9-16`).
- Hook code runs with no Node. It cannot import the qmd SDK (`.claude/types/claude-code.d.ts:17-18`).
- A hook can run a host command with `$.process.run`. The default timeout is 30 s, the maximum is ten minutes, and it is CLI-only (`.claude/types/claude-code.d.ts:3016-3038`).
- A hook can call a tool on an MCP server that Claude Code is connected to with `$.mcp.call` (`.claude/types/claude-code.d.ts:2366-2387`). The user must configure that server; the plugin does not start it.
- The model calls `om_recall` when it is visible and named in the memory. Hiding it behind ToolSearch gave about 0 calls per run (`docs/plans/om-direction.md:11`).

### 7.1 (a) Backend or second ranker for `om_recall` in one session

**What it would need.** Write each transcript block to its own file (thousands per session), keep a collection per session, and run `qmd update` as the transcript grows. `om_recall` would shell out to `qmd search --json` and map files back to `<file>:<line>` references.

**Costs.**
- Install: Node >= 22 and a global npm package on every user's machine (section 4.1).
- Latency: one new process per search, plus `qmd update` over the session's files first. Lex mode loads no model. Hybrid mode loads models per process unless a daemon runs (section 4.2).
- Disk: a second copy of the transcript text in SQLite, plus vectors if embedded.

**Risks.**
- qmd ranks files. Our needed result is a block. One file per block works around this, but it also changes BM25's length normalization and the dedup step.
- `search` is BM25. We measured BM25 against whole-term ranking and kept whole-term ranking (`docs/bench/2026-09-25-bm25.md:52,120`). qmd's compound-phrase rule fixes the `shard-101` miss, but `om_recall` already fixes it (`hooks/recall.ts:565-569`).
- Hybrid mode adds semantic matching. It also adds 2.25 GB of models and up to ~4.5 GB RSS per concurrent query on CPU (#942).
- A hard dependency on an external binary breaks recall for users who do not have it.

**Off the critical path?** Recall is not on the compaction path. Indexing could run in the background. The search call itself is on the model's turn.

**Verdict: no.** It duplicates what `om_recall` does in-process, at a much higher install and runtime cost. The measured gain would have to come from the semantic half. We have no evidence yet that our misses are semantic.

### 7.2 (b) Cross-session long-term memory tier

This is the user's idea: keep short-term notes as markdown; after ~2 days, promote the important ones to long-term; a new session can find "what we decided about X last week".

**What it would need.**
1. **Promotion by code, from originals.** The Reflector keeps the gist and drops specifics. So promote the source, not a rewrite. Each observation already carries a source time range. The promotion step copies the verbatim transcript blocks in that range (user messages, 🔴 constraints, the decision turn) into a markdown file. The observation text is the heading. The original is the body.
2. **A stable directory**, for example one per project, outside the per-session `$.store`. The 30-day prune (`hooks/prune.ts:9,108-118`) must not delete it.
3. **A promotion trigger off the compaction path.** For example, at session start or on a timer (`$.timer.after` / `every`, `.claude/types/claude-code.d.ts:2977,2987`), promote notes older than ~2 days from sessions that have ended.
4. **A visible way to search it.** The model rarely calls a tool it cannot see. So extend `om_recall` (for example a `scope: "past"` argument) and name it in the memory's standing note. A separate qmd MCP tool would be one more tool the model has to discover.
5. **A search backend.** Two options:
   - Our own whole-term search over the promoted markdown files. No install. Same ranking as today.
   - qmd, if the user has it. The plugin runs `qmd --index om search --json` (lex, no model) or `query` through `$.process.run`, with a named index so it does not mix with the user's own collections (`qmd:README.md:1061-1062`). Fall back to our own search when qmd is absent.

**Costs with qmd.**
- Install burden: Node >= 22, `npm install -g @tobilu/qmd`, and native builds. For semantic search, 2.25 GB of models on first use.
- Disk: the markdown files, the SQLite copy, and vectors. Promoted originals are much smaller than full transcripts.
- Latency: lex search needs no model load. Hybrid `query` per CLI call loads up to three models. The maintainers report ~10 s warm with a daemon (`qmd:CHANGELOG.md:1039`). Cold CLI calls are slower: section 8 measured 56.5 s cold with reranking, and 2.2 s warm through the SDK without it.
- Indexing: `qmd update` rereads and hashes the whole collection each run (section 3.5). `qmd embed` then embeds only new content.

**Risks.**
- Stale decisions. A decision from last week may have been reversed. Promoted files need dates, and search results must show them.
- Privacy and scope. Past transcripts of one project must not surface in another. Use one collection per project.
- A second store of the user's text on disk, outside Claude Code's own session files.
- qmd memory spikes on CPU-only machines (#942). Lex mode avoids them.
- The hybrid pipeline can move an exact identifier out of the top 3 (section 5).

**Off the critical path?** Yes. Promotion and `qmd update`/`qmd embed` can run in the background, outside compaction. Search runs only when the model calls it.

**Verdict: plausible, as optional.** qmd's real value here is semantic search over a growing cross-session corpus ("what did we decide about retries"). Its lex mode adds little over our own search. Build the tier so it works without qmd. Use qmd only when present. Issue #21 (durable memory tier) is the place to track this.

### 7.3 (c) Other fits

- **Write markdown, let the user's qmd find it.** The plugin writes promoted originals as dated markdown files in a documented directory. A user who already runs qmd adds one collection. The plugin carries no qmd code, and qmd's MCP server serves the search. This costs us nothing in install burden. It fails the visibility rule unless the standing note names the qmd tool.
- **Ideas to borrow, not code.**
  - The strong-signal skip: when the cheap ranker is decisive, skip the expensive stage (`qmd:src/store.ts:426-427,5560-5580`).
  - Position-aware blending that protects the retrieval top 3 from a reranker (`qmd:src/store.ts:5781-5788`).
  - Content-addressed caching of model results, keyed by query, model, and chunk text (`qmd:src/store.ts:1237-1243`).
  - `qmd bench`-style fixtures (query, expected file, expected top-k) for recall tests (`qmd:README.md:1140-1207`).
- **Not a fit: replacing the Observer or Reflector.** qmd retrieves; it does not summarize. It cannot make the compacted context smaller.

## 8. Hands-on test on our data (2026-09-26)

qmd 2.8.3 on node 24, CPU only (the GPU driver was broken, so model timings are pessimistic). Scripts, raw results and scored tables are in `.scratch/qmd/` (gitignored; `REPORT.md` there has every query). The queries and the pass rules were written by the tester, and the samples are small.

### 8.1 Install and cost

- The install took about 10 s. npm 11 blocked the native install scripts until `better-sqlite3` and `node-llama-cpp` were approved.
- Disk: 3.1 GB (2.2 GB of models, 856 MB of packages).
- Building the vector index is slow on CPU: about 5 chunks/s. 3.2 MB of transcript (3,308 chunks) took 682 s. The FTS update took 3–5 s.

| Operation | Time | Peak RSS |
|---|---:|---:|
| `qmd search` CLI, cold (BM25) | 0.11 s | 70 MB |
| SDK lex search, warm | 1–4 ms | 75 MB |
| SDK vector search, first call / warm | 1.4 s / 43 ms | 750 MB |
| SDK hybrid, no rerank, first / warm | 4.5 s / 2.2 s | 3.6 GB |
| SDK hybrid with rerank (40 candidates) | 27–69 s | 4.9 GB |
| `qmd query` CLI, cold | 56.5 s | 4.7 GB |

### 8.2 Role (a): search within one session

48 queries over 3 real transcripts (`om-orchestration`, `om-v04`, `firstmate-11`), against `om_recall`'s own search from `hooks/recall.ts`. Hit@k counts the right passage in the top k.

| Engine | Identifiers (8) hit@1 | Keywords (18) hit@3 | Reworded (22) hit@5 | Median time |
|---|---:|---:|---:|---:|
| `om_recall` | 8 | 16 | 4 | 11 ms |
| qmd lex | 6 | 14 | 2 | 1 ms |
| qmd vector | 7 | 14 | 13 | 43 ms |
| qmd hybrid | 7 | 16 | 12 | 2.2 s |
| qmd hybrid + rerank | – | – | 13 | 51 s |

- qmd lex returns nothing for any query that contains `/` (`hooks/prune.ts`, `lllyasviel/vcc`), and nothing for questions in natural language.
- For `shard-101`, qmd ranked the right ~900-token chunk third. `om_recall` put the exact checksum line first, which is what verbatim recall needs.
- Reworded questions are `om_recall`'s gap. Example: "user dislikes the browser editor session" found "i dont like lavish" at rank 1 with qmd vector search.

### 8.3 Role (b): across sessions

12 "what did we decide about X" questions whose answers are in earlier sessions (why BM25 was rejected, why the fork handoff was rejected, the Reflector thresholds, and others), over three corpora:

- **Stored Observer notes** hold the answer to only 7 of the 12. Notes for the sessions with the five rejected approaches were compressed or pruned. For those 7, qmd vector search found each answer at rank 1–2, reworded questions included.
- **Raw transcripts** (5.3 MB, 26 min to embed): 7–8 of 12 in the top 5 for reworded questions. Many hits were turns that quoted `docs/plans`.
- **`docs/plans` and `docs/bench`** answered most reliably. `om_recall`'s ranking, with no model, found 12 of 12 keyword questions and 10 of 12 reworded ones in the top 5.

### 8.4 What the test shows

- Do not put qmd behind `om_recall` for exact recall. Our ranking is as good or better, needs nothing installed, and returns the exact line.
- qmd's value is vector search for reworded questions. It could serve as a fallback for an `om_recall` search that finds nothing, with the index built in the background.
- Only a process that keeps the model loaded is fast enough for that (43 ms warm, 1.4 s cold). A per-call CLI is not. Nothing qmd does belongs on the compaction path.
- For a long-term tier, the source matters more than the engine. Written decision records beat both notes and raw transcripts. Stored notes miss what pruning and reflection dropped, which supports promoting originals, not rewrites (section 7.2).
- qmd's MCP server started and listed its four tools. It was not registered with Claude Code or timed in a live session.

## 9. Evidence gaps

- The timings in section 8 are CPU only, and two long jobs overlapped for about 10 minutes.
- Re-embedding cost for an appended file is inferred from the hash-keyed schema, not measured.
- Porter stemming of hex SHAs was not checked.
- Whether the Claude Code engine lets a plugin start qmd's HTTP daemon and keep it alive was not checked. `$.process.run` is one-shot and holds the call while the child writes (`.claude/types/claude-code.d.ts:3021-3028`).
