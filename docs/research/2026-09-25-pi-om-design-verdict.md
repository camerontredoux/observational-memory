## Verdict

From code only, ours (the Claude Code plugin at `/home/cameron/work/mods/observational-memory`) is the better compaction plugin design, and I'm confident in that call. Across all four layers that decide what a working model can recover after compaction — observation, condensation, compaction itself, and recall — ours wins on the specific question asked: exact user constraints, task state, identifiers, and recoverable detail. The margin is not uniform: PI's Observer call shape (multi-call loop with self-paced coverage and schema-validated writes) and its BM25 ranking with regex-safety are genuinely better engineered pieces that ours should copy. But ours wins the load-bearing structural bet common to every layer — a first-class, code-enforced, never-condensed constraints/corrections tier, verified-before-accept condensation with a safe no-op fallback, verbatim-or-omitted compaction fields with a hard fallback to the host's stock compaction, and a wider, more precise, more stably-addressed recall corpus. PI's most attractive asset — a durable, cross-session `.memory/` filesystem — is a capability ours lacks outright and is worth adding, but it doesn't offset PI's weaker guarantees on the in-session question this comparison was scoped to.

## Scorecard

| Component | Winner | One-line reason |
|---|---|---|
| Observation | Ours | Bounded/marked truncation, real tool-outcome flags, clamped timestamps, and a verbatim constraints tier beat PI's unbounded tool text, no-outcome-flag, unclamped timestamps, and one real correctness bug (permanent silent gap on observer failure) |
| Condensation (Reflector vs Consolidator) | Ours | Verified, bounded, retried condensation with a safe no-op fallback and a code-enforced verbatim constraints lane beats unconditional trust-on-exit with no floor and no constraint concept at all |
| Compaction | Ours | Verbatim-or-omitted fields with adaptive budgets and a hard fallback to the host's stock compaction beat heuristic extraction/ranking with an unimplemented "critic tier" backstop |
| Recall | Ours | Whole session-chain + subagent corpus with stable file:line refs and targeted ID/phrase-matching fixes beat a single-session-file corpus with substring/ID false positives, even though PI's BM25 ranking is more principled |

## Per-component detail

### Observation
Deciding differences:
- **Failed-chunk recovery.** Ours never commits a failed chunk, so it's retried indefinitely (`hooks/register.ts:1043-1086`, `hooks/register.ts:293-299`). PI advances its dispatch watermark synchronously before the call and never rolls it back on failure (`src/hooks/observer-trigger.ts:96`, `:159-161`), so a failed chunk is silently and permanently skipped until process restart (`src/runtime.ts:42-49`, `src/index.ts:49`). **PI bug, high severity** — real, confirmed data loss.
- **Tool-result size handling.** Ours caps tool results at 5,000 tokens with an explicit "om_recall can retrieve" marker (`hooks/register.ts:186-195,349`). PI applies no cap at all (`src/ledger/serialize.ts:61-69,86`) — and ships an unused `truncateRecordContent`/`MAX_RECORD_CONTENT_CHARS` helper (`src/ledger/serialize.ts:21-28`) that is dead code, confirming an abandoned intent to cap. **PI bug, medium severity.**
- **Tool success/failure fidelity.** Ours labels `(error)` only from the host's own flag, never inferred (`hooks/register.ts:347-349`). PI's label carries no outcome flag at all (`src/ledger/serialize.ts:86`).
- **Verbatim constraints tier.** Ours separates 🔴 corrections into a never-condensed, replace-chained ledger (`hooks/register.ts:464-512`; `hooks/prompts.ts:8-12,63-69`). PI has no constraint concept anywhere (`agent/observer/prompt.ts:29-35`, flat `Observation` type in `src/ledger/types.ts:53-57`).

What ours should take: PI's multi-call `record_observations` loop with a running coverage receipt (`agent/observer/tool.ts:42-77`) and its exact-duplicate suppression, and — found on adversarial re-read — its **schema-enforced tool call** (typebox pattern/minLength, `agent/observer/tool.ts:8-22`), which rejects malformed input at the boundary. Ours instead silently appends an unrecognized line onto the previous observation with no error and no retry (`hooks/register.ts:538-541`) — a quieter corruption mode than PI's loud, retried failure.

### Condensation (Reflector vs Consolidator)
Deciding differences:
- **Verification before trust.** Ours only installs a reflection if it lands in a `[floor, target]` token band, retrying up to 4 times, else leaves the ledger unchanged (`hooks/register.ts:1116-1144`). PI trusts a clean exit unconditionally and tombstones the whole batch with no floor, diff, or retry (`.../src/hooks/consolidator-trigger.ts:131-148`); its own prompt licenses silent loss ("Discarding clear noise is fine and expected", `agent/consolidator/prompt.ts:47`). **PI bug, high severity** — and its own code comment names an intended "critic tier" safety net that was never built (`consolidator-trigger.ts:16`), confirmed absent from source.
- **Constraint survival.** Ours excludes 🔴 lines from the condenser entirely by code (`hooks/register.ts:1113-1119`; Reflector forbidden from writing 🔴, `hooks/prompts.ts:121-129`). PI has zero occurrences of "constraint" in its codebase; the consolidator is told to "REWRITE... delete the obsolete statement" over every observation, including user assertions (`agent/consolidator/prompt.ts:20`).
- **Reachability.** Ours renders all condensed material into the live context for free (`hooks/register.ts:796-810`). PI moves it to disk, reachable only via a one-line index summary plus a tool call (`src/memory/index-render.ts:47-58`) — mitigated, but not equalized, by PI also shipping a full-transcript `om_recall` backstop (`src/vcc/tools/recall.ts:18-45`), which the original review underweighted.
- **Preserving the arc of the work.** Ours ranks "what was tried, what failed and why" explicitly (`hooks/prompts.ts:131-144`). PI's consolidator is told to write "current-state prose, not a changelog" and delete "was X, now Y" cruft (`agent/consolidator/prompt.ts:19-20,26-32`).

What PI has that ours lacks entirely: a durable, cross-session `.memory/` topic-file substrate (`src/memory/paths.ts`). Worth adding as an optional layer, but should keep ours' verify-before-accept and verbatim-constraint guarantees rather than PI's trust-on-exit model.

### Compaction
Deciding differences:
- **Verbatim-or-omitted fields.** Ours' memory message holds user constraints, the exact latest request, and capped user-message history as whole-or-omitted verbatim fields with explicit budgets (`hooks/register.ts:61-69,711-719,731-757`). PI's session brief is built from regex/heuristic extraction (goals, preferences) with no guarantee any field is quoted byte-for-byte (`.../src/vcc/extract/goals.ts`, `preferences.ts`).
- **Failure fallback boundary.** Ours degrades all the way to the host's own stock compaction on `OVER_BUDGET`/`OVER_CAP`/`MEMORY_ALONE` (`hooks/register.ts:766-770,1399-1409`) — a bug in ours can't make compaction worse than doing nothing custom. PI's fallback stays entirely inside its own VCC pipeline (`.../src/compaction/coordinator.ts`), so a shared bug affects both normal and fallback paths, and its own "critic tier" mitigation (see above) was never built.
- **Adaptive budgets.** Ours computes its budget from the session's own measured token/character density (`hooks/register.ts:1375-1381`). PI's budgets are static defaults (`.../src/vcc/config.ts:26-31`).
- **Long-term recall depth (PI wins).** PI's `.memory/` filesystem is a durable, directly browsable substrate outside the compaction pipeline (`.../src/memory/paths.ts:1-22`). Ours relies on `om_recall` over the raw transcript only.

Risk noted on ours: constraints exceeding `CONSTRAINTS_MAX_TOKENS=8,000` causes a full bail to built-in compaction rather than graceful degradation (`hooks/register.ts:767,1409`) — low severity but a real cliff.

### Recall
Deciding differences:
- **Corpus scope.** Ours follows the whole chain of continued/resumed transcript files (up to 20) plus subagent transcripts (`hooks/recall.ts:271-304,307-377`). PI is explicitly scoped to the single current session file with no subagent path (`.../src/vcc/tools/recall.ts:32-33,76-82`). **PI risk, high severity** for long or delegated sessions.
- **ID/short-token precision.** Ours splits compound tokens on `_`/`-` in scoring itself, guarding against "101" matching inside "101047290" (`hooks/recall.ts:556-561,638-642`). PI's BM25 scoring matches raw substrings with no such guard in the scoring path, only in a separate absence check (`.../src/vcc/core/search-entries.ts:156-162,200-217,549-556`). **PI risk, medium.**
- **Quoted phrases.** Ours parses `"phrases"` as a unit (`hooks/recall.ts:556-579,592-636`). PI has no phrase syntax at all (`.../search-entries.ts:123-131,526-529`).
- **Regex query trigger.** Ours uses an explicit `/pattern/flags` delimiter (`hooks/recall.ts:563-571`). PI heuristically detects regex metacharacters, which its own comments say misfires on ordinary punctuation ~47.5% of the time (`.../search-entries.ts:497-524`). **PI risk, low.**
- **Where PI wins:** BM25-lite ranking with an empirically-tuned noise floor (`.../search-entries.ts:164-217,362-433`) is more principled than ours' hand-rolled scoring, and it defends against ReDoS/catastrophic backtracking on regex queries (`hasNestedQuantifier`, wall-clock budget, `.../search-entries.ts:44-96,109-121`) — ours' `/regex/` mode has no such guard, a real robustness gap found on adversarial re-read.
- **A real PI-side inconsistency found on re-read:** `expand:[N]` re-derives its snippet from a message's clipped `summary`, which never includes tool-call argument text, even though search scoring itself does fold in that text (`.../recall-excerpts.ts:110-115` vs `search-entries.ts:254-307`, `render-entries.ts:13-52`). So expanding the very entry search just matched on can come back empty. Ours has no equivalent gap (`hooks/recall.ts:643-687,778-804`).

## What each side should take from the other

Ours should adopt:
- PI's multi-call, self-paced Observer loop with a coverage receipt and in-call exact-duplicate dedupe (`agent/observer/tool.ts:42-77`).
- PI's schema-validated observation-writing call boundary, to close ours' silent-merge parsing failure mode (`hooks/register.ts:538-541`).
- PI's durable, cross-session `.memory/` topic-file substrate as an optional layer, kept under ours' verify-before-accept discipline.
- PI's BM25-lite ranking with its tuned noise floor, and its ReDoS guard/time budget on regex search.

PI should adopt:
- Ours' bounded, marked tool-result excerpting with a recoverability cue, instead of an uncapped tool-result text path.
- Ours' host-reported tool success/failure flag instead of inferring outcome from text.
- Ours' verified-before-accept condensation (size band + retries + no-op fallback) instead of trust-on-clean-exit.
- Ours' first-class, never-condensed constraints tier.
- Ours' whole-session-chain + subagent recall corpus, and its compound-token/quoted-phrase precision fixes.

## What the code cannot tell us

- Whether PI's actual quality of paraphrase (via its Amos-derived Observer prompt, which is a documented sibling of ours' own Observer prompt) matches or beats ours' in practice — both systems paraphrase everything outside the verbatim-protected tier, and only a live transcript comparison can show how often that paraphrase drifts from the original meaning.
- Whether PI's single-session-file scoping is actually as costly as it looks — if PI's host keeps one continuously-appended file across what Claude Code would treat as separate continuation files, the "corpus completeness" gap may be smaller in practice than the code alone suggests.
- Real-world frequency of ours' unbounded-regex-hang risk and PI's permanent-observation-gap-on-failure — both are confirmed as possible in code, but only live/adversarial runs show how often they actually trigger.
- Whether PI's host actually rejects an invalid `record_observations` tool call outright (structural enforcement) versus coercing it — the enforcement point lives outside the reviewed files.
- End-to-end effect on task continuation quality (the actual "can the model pick up the task correctly" outcome) — this review is structural/code-only and explicitly excludes prior benchmark numbers, so it cannot confirm the ranking holds under real compaction runs.

## pi-OM's own benchmarks, and how they compare with ours

pi-observational-memory has run three kinds of benchmark on itself: (1) live A/B/C fact-recall quizzes against a rival extension ('pi-blackhole') and against its own pre-VCC build — these are not comparisons with our plugin at all, they're pi-OM benchmarking design variants of itself and a competitor; (2) a well-iterated internal recall-tool ablation (4 dated slices, quality held at 27/27 or 54/54 while cutting recall cost and latency ~90%+) that never regressed quality but converged on the same ~16KB response-budget cap our recall.ts independently arrived at; (3) a self-acknowledged weak consolidator-timing stress test that its own authors say proves nothing about real retention quality, and for which no proper replay-based evaluation had been built as of the document.

The one place where our plugin and pi-OM were actually run through the identical test (same prompts, same files, same scoring code) is /tmp/om-bench/pi-results.jsonl vs the matching records in our own results.jsonl, for three scenarios (reversed-constraint, repeated-compaction, pending-approval). At n=3 per side, results are roughly tied — one failure out of six-to-nine relevant runs on each side — which sits inside our own documented 56-68% run-to-run noise floor, so this data cannot support a "ours is better" or "pi is better" claim on quality. It does show our plugin costs 2-4x more per run in this sample, but that tracks Sonnet vs gpt-5.6-sol list pricing rather than plugin efficiency, since the cost fields aren't model-normalized.

A pre-existing document in this repo, docs/archive/research/2026-09-24-pi-om-comparison.md, already did a substantial version of this exact comparison (both design-level and the same-harness benchmark angle) and reached a compatible conclusion: the cross-implementation quality data is too thin to declare a winner, but several of our plugin's specific design choices (verbatim-protected corrections tier, deferred recall-tool visibility with a large measured effect, floor/retry verification on condensation, recall corpus that chains sessions and subagents) have no equivalent found in pi-OM's code, while pi-OM's durable on-disk cross-session memory has no equivalent in ours. That document is slightly stale — it references pi-results.jsonl as having only 6 records; it now has 9, including the pending-approval scenario I found — but its overall benchmark-strength conclusion still holds. The most valuable next benchmark step neither side has run: pi-OM has never been run through our recall-required scenario, which is exactly where our biggest measured design win (deferred recall visibility) shows up.

The only genuinely apples-to-apples data is /tmp/om-bench/pi-results.jsonl (9 records, produced by this repo's own scripts/bench-pi.ts against pi-observational-memory-vcc v0.85.1 on openai-codex/gpt-5.6-sol) versus /tmp/om-bench/results.jsonl's matching om+recall records for the same three scenario ids (reversed-constraint, repeated-compaction, pending-approval) on Claude Sonnet. Ours: reversed-constraint 6/6, repeated-compaction 5/6, pending-approval 5/6 (one fallback-to-built-in-compaction failure in each of the latter two, across old+new plugin versions). pi-OM: reversed-constraint 3/3, repeated-compaction 3/3, pending-approval 3/3-valid-but-1-task-failure. Cost columns are not comparable as-is (Sonnet list pricing vs gpt-5.6-sol list pricing, both marked 'estimated'). No pi-OM data exists yet for our recall-required scenario, which is the scenario carrying our plugin's single largest measured design win (deferred om_recall visibility, 1/3 -> 6/6 task success per docs/plans/om-direction.md) — that comparison has not been run.
