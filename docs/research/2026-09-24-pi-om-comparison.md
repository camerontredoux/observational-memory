# pi-observational-memory vs observational-memory (Claude Code plugin)

> **Checked after the workflow (2026-09-24).** Two corrections take precedence over the text below:
> 1. PI's on-disk memory is **per session**, not cross-session. It lives in `.memory/<sessionId>/`, and a new session copies it only from its parent (fork, clone, or new-with-parent) (`pi-observational-memory-vcc/src/memory/session.ts:58-75`). Read "cross-session" for PI as "durable within one session line".
> 2. `/tmp/om-bench/pi-results.jsonl` now holds 6 records: 3 reversed-constraint runs (`om_recall` not called) and 3 repeated-compaction runs (1 `om_recall` call and 1 hit each). The report was written when fewer repeated-compaction runs existed.

## 1. Bottom line

- Both systems replace built-in compaction with the same shape: an Observer that writes timestamped notes from raw transcript chunks, a condensation step, and a recall tool. They diverge sharply on where memory lives after that.
- **OURS** keeps everything in one growing, self-condensing in-context ledger inside Claude Code's `$.store`. **PI** splits into a small bounded in-context pool plus durable on-disk Markdown topic files (`.memory/<sessionId>/`) written by a separate consolidator process — genuine cross-session, durable memory ours does not have.
- OURS has a verbatim, permanently-protected tier for user constraints (`<corrections>`, marked 🔴, guarded by an over-cap fallback to built-in compaction). PI's consolidator is instructed to *rewrite* topic files to "current truth," with no equivalent verbatim-preservation guarantee — a real robustness gap, though unconfirmed by live-session testing.
- OURS defers `om_recall`'s tool description until after the first compaction, which its own docs credit with a large real measured jump: recall-required task success from 1/3 to 6/6, recall calls per run from 0 to ~1 (`docs/plans/om-direction.md:9,11`). PI has no equivalent deferred-visibility mechanism.
- PI's recall tool only searches the current session file, no chained/continued sessions, no subagent transcripts (`pi-observational-memory-vcc/src/vcc/tools/recall.ts:32-33`, tool description states this limitation itself). OURS chains up to 20 linked files plus subagent transcripts (`hooks/recall.ts:271-377`).
- Both recall implementations converged independently on the same ~16,000-byte/char final-response budget and similar multi-region excerpting (~3 windows per hit, rarest-term anchoring) — strong cross-validation that this shape is close to right on both sides.
- The only true head-to-head run through the same benchmark harness is thin: one scenario (reversed-constraint), 3 runs per side, on **different models** (Sonnet 5 vs gpt-5.6-sol), both hit 100% task success, but PI's fact-carrying came entirely from its verbatim kept-tail in all 3 runs, not its Observer memory, and `om_recall` was not called in those 3 runs. A 4th PI record (repeated-compaction) does show a successful `om_recall` call, which the original research pass missed.
- Given ours' own documented noise floor (56–68% run-to-run variance on the same code; 3+ runs per arm needed for any claimed gain, `docs/plans/om-direction.md:18,27-28`), the existing cross-implementation data cannot support a general "ours beats PI" or "PI beats ours" claim on quality. It supports narrower, code-level claims about specific design choices.

## 2. Side-by-side: key design choices

| Dimension | OURS (Claude Code plugin) | PI (pi-observational-memory-vcc) |
|---|---|---|
| Memory location | Single in-context ledger in `$.store`, condensed in place | Bounded in-context pool + durable on-disk Markdown files (`.memory/<sessionId>/`) |
| Long-term retention | Everything degrades toward one shrinking message; nothing leaves context | Old material permanently offloaded to topic files + `JOURNEY.md`, survives across sessions |
| Observation format | Free-form prose in one text completion, 4 priority markers (🔴🟡🟢✅) | Tool call `record_observations`, minimal schema `{timestamp, content, tokenCount}`, no priority tier |
| User-constraint durability | `<corrections>`: verbatim, permanent, budget-guaranteed (`CONSTRAINTS_MAX_TOKENS=8,000`), over-cap falls back to built-in compaction | No verbatim-preservation guarantee found; consolidator instructed to "REWRITE... to current truth" |
| Condensation | In-place Reflector pass, floor/retry ladder (`REFLECT_FLOOR=0.4`, up to 4 attempts), race-guarded | Consolidator subprocess drains pool into files; trusted unconditionally on clean exit, no size/content check |
| Compaction trigger | Passive: invoked by Claude Code's own `session.compact` event | Active: PI's plugin polls context usage itself and calls `ctx.compact()` |
| Deterministic fallback brief | `compileBrief` (code, not model) covers spans the Observer never reached; explicit `FLOOR_NOTE` marker | VCC brief is always deterministic/code-compiled, computed after (not independent of) Amos's cutoff resolution |
| Recall corpus scope | Chains up to 20 linked session files + subagent transcripts | Current session file only (tool description states this limitation) |
| Recall ranking | Whole-term-first gate, IDF fallback | BM25-lite with empirically tuned relative floor + hard cap of 50 |
| Recall tool visibility | Deferred/hidden via ToolSearch until first compaction, then always visible | Always registered, no deferred-visibility mechanism found |
| Recall response budget | `RESPONSE_MAX_CHARS = 16,000` chars | `OUTPUT_BUDGET_BYTES = 16,000` bytes — essentially the same cap, reached independently |
| Cost tracking | Per-call USD cost live-tracked and surfaced via `om_stats` (corrected: was initially misreported as absent) | `om.cost` ledger entries, summed across all branches (never rolled back under `/tree`) |
| Stats/status surface | Persisted, cross-session historical stats (`om_stats`, percentiles) | Live, non-persisted `/om:status` TUI, plus manual `/om:compact`/`/om:consolidate` overrides |
| Environment/git snapshot in compacted context | Yes — fresh `git status`/branch/HEAD read at every compaction | Not found — no equivalent in reviewed code |
| Codebase status | Single implementation | Local checkout carries an unpushed 8,300-line VCC layer (8 commits) on top of upstream, which has no such layer |

## 3. Per-dimension detail

### 3.1 Pipeline

Both chunk raw transcript at ~10,000 tokens (`hooks/register.ts:35-40,54-55`; `pi-observational-memory-vcc/src/config.ts:53-70`), run up to 4 Observer calls in parallel, and use a low-thinking model for observation. OURS runs Observer/Reflector calls in an isolated `/tmp` `pi -p` completion with no persisted worker session; PI spawns each chunk as a fully separate, recorded OS subprocess/session (`spawnWorker`, tagged `om-observer-<runId>`), making failed or odd runs independently inspectable in PI's session browser (`spawn/launch.ts:1-8`).

Observer output formats differ in kind, not just detail: OURS emits free-form prose with 4 priority markers and a structured `<continuation>` handoff record (`hooks/prompts.ts:8-13,15-99`); PI emits a `record_observations` tool call against a deliberately minimal schema — `{timestamp, content, tokenCount}` — explicitly stripped of priority/relevance/id fields relative to an earlier internal version (`pi-observational-memory-vcc/src/ledger/types.ts:1-58`, "Trimmed from OM V3" comment verbatim).

Condensation diverges architecturally. OURS's Reflector rewrites older observations in place when the rendered memory exceeds 40,000 tokens, targeting 20,000, always leaving the newest 12,000 untouched and 🔴 corrections untouched, with a floor-and-retry loop that discards under-condensed output (`hooks/register.ts:1091-1159`; `hooks/prompts.ts:170-179`). This directly followed a measured failure: v1.2.0 crushed memory to 18% of needed identifiers (1/10 kept); the floor+target-band fix raised that to 81% (8/8 kept) (`docs/plans/om-direction.md:14`). PI's consolidator instead drains overflow (pool > 15,000 tokens, 150% of the 10,000-token target — corrected from an earlier "200%" arithmetic slip) into durable topic files, and is *trusted unconditionally* on clean exit: it does not report which observations it filed, so the orchestrator tombstones the whole handed batch by intersection, with no size/content sanity check before that happens (`pi-observational-memory-vcc/src/hooks/consolidator-trigger.ts:1-16,60-90,118-143`, "Trust the consolidator..." / "critic tier's job to catch" verbatim). PI's own comments admit this verification gap is unbuilt.

Compaction triggering is a platform-level asymmetry: OURS is invoked by Claude Code's own `session.compact` event (passive); PI's plugin polls its own context-usage estimate every `turn_end` and calls `ctx.compact()` itself (active) (`hooks/register.ts:1286`; `pi-observational-memory-vcc/src/hooks/compaction-trigger.ts:15-60`). This is likely a host-API difference, not a design preference — worth raising with Claude Code's hook API maintainers as an open question rather than treating as something to imitate directly.

Cost tracking is not a gap for OURS as originally reported: per-call USD cost is captured live from each completion's `usage.cost.total` (`hooks/register.ts:596,599`) and surfaced with per-call averaging through `om_stats`/`hooks/stats.ts:249-252`. The real remaining difference is scope: PI's `sumSessionCost` explicitly sums across every branch so spend never rolls back under `/tree` (`ledger/types.ts:143-168`); whether ours' stats has an equivalent branch-scope distinction was not checked.

The local PI checkout's entire VCC layer — deterministic, non-model compaction/recall (`goals.ts`, `preferences.ts`, `commits.ts`, `files.ts`, `rank.ts`, `search-entries.ts`, `recall-excerpts.ts`) — is an unpushed, local addition (8 commits, +8,290/−174 lines) on top of upstream `pi-observational-memory`, which has none of this. Upstream is closer in scope to a pure Observer+consolidation system; the VCC comparison is against this local fork specifically.

### 3.2 Compaction (compacted-message structure)

OURS renders one `role: user` memory message: `<corrections>` (verbatim), `<observations>` (LLM-written, prioritized), an optional code-compiled `<session-brief>`, verbatim user messages, and a `<continuation>` handoff block including a fresh git-derived environment snapshot (`hooks/register.ts:796-812` — corrected line range; `hooks/register.ts:610-629` `environmentOf()`). PI concatenates two independently-produced artifacts: a deterministic VCC brief and an LLM-written "Amos" observation/journey block (`pi-observational-memory-vcc/src/compaction/format.ts:1-23`; `src/ledger/render.ts:1-41`). PI has no equivalent environment/git snapshot anywhere in the reviewed compaction code — a capability gap on PI's side, not OURS's.

On user-constraint durability: OURS's `<corrections>` block is a hard, budget-guaranteed channel (`CONSTRAINTS_MAX_TOKENS=8,000`; over that cap, compaction falls back to Claude Code's built-in compactor rather than truncating a constraint, `hooks/register.ts:767-768,1409`). PI's consolidator prompt explicitly instructs it to "REWRITE the file to reflect the new truth and delete the obsolete statement" (`agent/consolidator/prompt.ts:20`) — no verbatim-quote requirement, no priority-marker equivalent found anywhere in PI's observer or consolidator prompts. This looks like a genuine robustness gap on PI's side, though it is inferred from prompt text, not from observed output on a real session.

On fallback when the Observer fails: OURS has an explicit ladder — progressively shorter cuts, then dropped ranges, then a code-compiled floor brief marked `FLOOR_NOTE`, then built-in compaction as a last resort (`hooks/register.ts:1403-1467`). PI's deterministic VCC brief provides baseline structural coverage regardless of Amos's success, but it is *not* computed independently in parallel, as originally claimed — `compileVccSpan` is called after `compactAmosMemory` completes and consumes its cutoff/branch as direct inputs (`pi-observational-memory-vcc/src/compaction/coordinator.ts:33-50`). What is true is narrower: VCC's ranking doesn't consume the Observer's written text, so a failed chunk doesn't corrupt VCC's content — but VCC compilation is still sequenced after Amos's resolution step. On the Amos/LLM layer specifically, a failed Observer subprocess is not merely unretried — it is durably skipped: `dispatchedCoversUpToId` is set at dispatch time, before the subprocess runs, and `effectiveWatermarkId()` never rolls it back on failure, so that span's coverage is permanently absent from both the ledger and any future dispatch attempt for the rest of the process (`observer-trigger.ts:60-96,185-194`).

Repeated compaction chains differently. OURS rebuilds the full memory message every compaction from the ledger, re-parsing the previous message's `<corrections>`/`<continuation>`/user-messages forward (`hooks/register.ts:815+` `parseMemory()`), so per-compaction cost is roughly proportional to standing memory size. PI's configured "append" mode (the user's actual setting, `settings.json:40-44`) instead writes only a small immutable segment per compaction plus a mutable trailing summary, chained by sequence and re-projected by a context hook with cache invalidation (`src/vcc/details.ts:25-36`; `src/hooks/compaction-context.ts:1-32`; `src/vcc/compaction-chain.ts:90-183`, cache logic ~367-502). This bounds per-compaction recomputation at the cost of chain-length growth and real complexity (sequence validation, a documented append→rewrite fallback). PI also auto-rebases the chain once it exceeds 50% of the context window (`MAX_CHAIN_WINDOW_RATIO = 0.5`, `compaction-chain.ts:28,248-255`) — this figure is real and precisely sourced, correcting an earlier citation that pointed at a file not actually containing it.

### 3.3 Recall

Corpus scope is the sharpest asymmetry. OURS's `loadTranscript` walks the full session file chain (up to `CHAIN_MAX_FILES=20`, via continued-in links) plus every subagent transcript (`hooks/recall.ts:1-6,271-377`). PI's `loadAllMessages` reads only the current session file — no chaining, no subagent search — and its own tool description states this limitation directly (`src/vcc/core/load-messages.ts:10-38`; `src/vcc/tools/recall.ts:32-33`).

Ranking: OURS gates on whole-term matches first, falling back to IDF-weighted loose scoring only if nothing matches whole (`hooks/recall.ts:710-724`). PI uses BM25-lite (k=1.2, b=0.75) with an empirically-tuned relative noise floor (drop hits below 20% of top score, multi-term queries only) and a hard cap of 50 results before pagination (`src/vcc/core/search-entries.ts:164-217,362-433`). Both approaches are defensible; a head-to-head on ranking quality was not established by either side's existing documentation.

Both converged independently on the same final-response size ceiling: OURS's `RESPONSE_MAX_CHARS = 16,000` chars (`hooks/recall.ts:11-29`) and PI's `OUTPUT_BUDGET_BYTES = 16,000` bytes (`src/vcc/core/recall-excerpts.ts:1-7`) are essentially the same cap, and this was reached by two independent implementations — strong cross-validation, not a gap on either side. Multi-region excerpting also converged: both pick ~3 windows/lines per hit, ranked by rarest/most terms, spaced apart, with an overlong-line cap around the rarest matched term (`hooks/recall.ts:590-688`; `src/vcc/core/recall-excerpts.ts:15-96`).

Tool visibility is the clearest asymmetry in recall. OURS defers `om_recall`'s description behind ToolSearch until a summary exists in the session (`hooks/register.ts:1628-1634`), a change credited with taking recall calls from 0 to ~1 per run and recall-required task success from 1/3 to 6/6 (`docs/plans/om-direction.md:9,11`). No equivalent deferred/lazy tool-discovery mechanism was found anywhere in PI's extension (a search of PI's source found only an unrelated match — a noise-filter list entry naming "ToolSearch" as a tool to exclude from indexing, not a visibility feature). PI leans instead on a rich, always-visible tool `description`/`promptSnippet` (absence-reporting guidance, anti-repeat-query instruction) since the tool is never hidden (`src/vcc/tools/recall.ts:22-39`).

PI documents its own bounding history in detail: `RECALL_EFFICIENCY_PLAN.md` records dated, numbered ablation slices — an unbounded baseline returning up to 899,847 bytes / ~105,627 mean input tokens, cut ~90-94% by bounded expand at unchanged quality, then further call-count reductions (25→12→8 calls) from multi-region search and negative-coverage reporting, plus a real 691.6-second stall from a malformed 12,541-index `expand` argument that led to a hard `maxItems: 5` cap enforced at both schema and executor level. This fix is already shipped and re-benchmarked (182 tests across 24 files, 27/27 quality retained, responses averaging 1,094 bytes, never exceeding 1,954), not merely proposed. OURS has no equivalent written ablation history, but checking ours' own git history resolves an open question the original research left unanswered: `recall.ts`'s bounding constants (`SEARCH_MAX_HITS`, `SEARCH_MAX_CHARS`, etc.) were present from the tool's very first commit (`6a515b3`) — ours never went through an unbounded-recall phase the way PI's pre-`5f9abc6` baseline did.

Stats/status surfaces are near-opposite in kind: OURS's `om_stats`/`/om-stats` gives persisted, cross-session historical percentiles (`hooks/stats.ts:1-19`); PI's `/om:status` gives a live, non-persisted snapshot (observers in flight, pool vs targets, cost) plus a footer widget and manual override commands `/om:compact`/`/om:consolidate` that OURS has no equivalent of (`src/commands/status.ts:1-47`; `src/ui/status-controller.ts:1-80`; `src/commands/compact.ts:1-43`; `src/commands/consolidate.ts:1-47`).

### 3.4 Evidence

The only same-harness head-to-head is thin. `tests/eval/pi.ts` and `scripts/bench-pi.ts` convert a PI session into ours' scoring shape and drive a live PI run with the extension pinned to a 6,000-token kept tail matching ours (`tests/eval/pi.ts:1-24`; `scripts/bench-pi.ts:1-27`). Results in `/tmp/om-bench/pi-results.jsonl` actually contain **4 records, not 3** as the original research reported: 3 reversed-constraint runs plus a 4th, repeated-compaction run that the original pass missed entirely. All 4 are `task-success:true`. In the 3 reversed-constraint runs, the "tabs" constraint was carried only by PI's verbatim kept-tail, not its Observer memory, and `om_recall` was never called (`retrieval.calls=0`). But the 4th, repeated-compaction run *did* call `om_recall` once and succeeded (`retrieval.calls=1, hits=1`) — this directly refutes the blanket claim that PI's recall tool "was never called" in this comparison, and it means a second scenario has already been run live against PI with a matching old/new comparison available in `results.jsonl` (18 matching repeated-compaction records exist there already, no further live-run budget needed to compare them).

Cost comparison from the same 3 reversed-constraint runs is confounded: OURS ran Sonnet 5 (~$0.33–0.44/run), PI ran gpt-5.6-sol with mostly host-reported cost (~$0.08–0.11/run) — a ~3–5x gap that reflects model/price-table choice, not implementation efficiency, and should not be read as "PI is cheaper."

OURS's own broader evidence is far more extensive: 8 scenarios across plugin versions v1.0.0–v1.3.0 (`docs/bench/*.md`), the recall-visibility fix (1/3 → 6/6 on recall-required), and a stated noise floor of 56–68% run-to-run variance requiring 3+ runs per arm before trusting any delta (`docs/plans/om-direction.md:18,27-28`). PI's own internal A/B evidence (`/home/cameron/work/pi-memory-ab-results-2026-09-03-corrected/REPORT.md`, `/home/cameron/work/pi-memory-abc-luna-2026-09-03/REPORT.md`) compares PI's extension against a different third-party competitor ("pi-blackhole") and a pre-VCC "vanilla" variant — not against ours. Notably, PI's own luna-model A/B shows its VCC layer gave "no recall gain" over the simpler pre-VCC vanilla Amos, while increasing post-compaction context by 12.1% (5,529 → 6,200 tokens) — evidence from PI's own team that VCC's added complexity may not currently pay for itself, at least on their test.

Given both the thin single-scenario cross-model overlap and OURS's own stated noise floor, no confident aggregate "ours beats PI" or "PI beats ours" quality verdict is supported by current data.

## 4. What we could borrow from PI, ranked by expected value / effort

1. **Durable, on-disk, cross-session memory tier** (`.memory/<sessionId>/{INDEX.md,<topic>.md}` pattern). High value, high effort. Confirmed as a real, unaddressed gap: no filesystem writes exist anywhere in `hooks/register.ts` or `hooks/vcc.ts` (checked via `rg` for `writeFileSync`/`mkdirSync`/`.memory/`/disk writes — zero hits). Not discussed or rejected in `docs/plans/om-direction.md`, so this is open territory rather than something already decided against. This is the single biggest structural difference between the two systems and the clearest place ours currently loses durability that PI has.

2. **Live, in-session status surface** (PI's `/om:status`, in-flight Observer/Reflector count, distance to next threshold). Medium value, low-medium effort. Complements rather than replaces ours' existing persisted `om_stats` — no conflict with prior decisions. Useful for interactive debugging during a live session, which `om_stats`'s cross-session percentiles don't cover.

3. **Manual override commands** (`/om:compact`, `/om:consolidate` analogues). Medium value, low effort. Not discussed in `om-direction.md`. Straightforward to add, guarded the same way PI guards them (re-entrancy check, off-state check).

4. **Write dated, numbered ablation-evidence sections for recall's bounding constants**, matching PI's `RECALL_EFFICIENCY_PLAN.md` style. Low-medium value, low effort — this is a documentation practice, not a code change, and directly addresses a real audit gap (ours' bounds are currently justified only by inline comments, not a written before/after history).

5. **Recording Observer/Reflector calls as inspectable, resumable sessions** rather than isolated `/tmp` completions. Medium value, medium effort — depends on whether `pi -p` exposes an equivalent recorded-session mode. Improves debuggability of bad Observer output but doesn't change behavior.

6. **Fold richer recall usage guidance into the tool's own `description`/schema** (absence-reporting semantics, anti-repeat-query instruction), not only the post-compaction memory message. Low value given ours' deferred-visibility design already solves most of the problem PI's rich description compensates for — but cheap insurance in case a model reads the tool schema before any compaction has happened.

**Explicitly not recommended**, because ours already tested and rejected the closest analogue: PI's "always compute a separate deterministic VCC brief alongside the Observer memory" resembles ours' own rejected `vcc-brief` branch experiment, which scored within noise of Observer memory + recall while needing more recall prompting and cost, and was kept only as a fallback-path brief, not a permanent parallel structure (`docs/plans/om-direction.md:22`, Rejected section). PI's own internal luna-model A/B data supports this skepticism from the other side: their VCC layer showed "no recall gain" over their simpler pre-VCC vanilla Amos while increasing post-compaction context by 12.1%. Do not promote ours' fallback floor-brief to a permanent parallel-brief architecture on the strength of PI's example alone.

**PI's append-mode incremental compaction** (segments + trailing summary, avoiding full re-render each compaction) is worth knowing about but not currently worth porting: PI's own data shows it does not clearly beat a simpler rewrite-every-time baseline on recall quality, and it brings real complexity (sequence validation, cache invalidation, a documented append→rewrite fallback path). Revisit only if ours' full-rebuild-per-compaction cost becomes a measured bottleneck on very long sessions.

## 5. Where ours is ahead

- **Verbatim, permanently-protected user constraints** (`<corrections>`, 🔴 marker, budget-guaranteed with an explicit fallback to built-in compaction rather than truncation). PI has no equivalent found; its consolidator is told to rewrite to "current truth."
- **Deferred recall-tool visibility**, with a large measured real effect (1/3 → 6/6 on recall-required). PI has no comparable mechanism.
- **Recall corpus completeness**: chains continued sessions and indexes subagent transcripts; PI searches only the current session file, by its own tool description's admission.
- **Explicit floor/retry verification on condensation** (`REFLECT_FLOOR`, escalating compression levels, discard-and-retry on undersized output). PI's consolidator is trusted unconditionally on clean exit, with no equivalent sanity check — PI's own code comments flag this as unbuilt ("critic tier's job to catch").
- **Fresh git/environment snapshot** included in every compacted message. Not found anywhere in PI's reviewed code.
- **Live per-call USD cost tracking already exists** and is surfaced through `om_stats` — this was misreported as absent in the original research pass and should not appear as a borrow-from-PI item.
- **Persisted, cross-session historical stats** (percentiles, cost totals) as an audit trail; PI's live status numbers vanish when the session ends.
- **No unbounded-recall phase in git history** — bounding constants were present from `recall.ts`'s first commit, unlike PI's retrofit after a real incident.

## 6. Evidence gaps and suggested experiments

- Only one scenario (reversed-constraint) plus one incidental repeated-compaction record have been run head-to-head through the same harness, and on different models. Before drawing any quality conclusion, run the existing PI harness (`scripts/bench-pi.ts`) on the recall-required scenario specifically — the scenario where ours' most distinctive design choice (deferred tool visibility) showed its largest measured effect (1/3 → 6/6). No comparable PI data exists for this scenario at all.
- Re-run the reversed-constraint comparison with matched models on both sides (or explicitly control for model in the cost analysis) before citing any cost-per-run delta between the two systems.
- The 18 existing repeated-compaction records in `/tmp/om-bench/results.jsonl` can be compared against the newly-found PI repeated-compaction record without spending further live-run budget — do this analysis before running anything new.
- Confirm whether PI's consolidator ever preserves a user's exact wording in practice, versus always paraphrasing to "current truth" — this needs a real session trace, not just prompt-text inspection, since the current claim rests only on the consolidator's instructions, not observed output.
- Check whether `hooks/stats.ts` tracks cost with the same "never rolled back across branches" semantics as PI's `sumSessionCost` — the one specific, still-open piece of the cost-tracking comparison.
- `src/vcc/core/{rank,search-entries,recall-excerpts,brief}.ts` versus `hooks/vcc.ts`/`hooks/recall.ts` at matching depth was flagged as out-of-scope in the original research and remains unread in comparable depth — the natural next research pass for the recall/brief-building comparison specifically.
- PI's `IMPLEMENTATION_REPORT.md`, `PLAN.md`, `RECALL_EFFICIENCY_PLAN.md`, and `CONSOLIDATOR_OPTIMIZATION_NOTES.md` were read only in part; a full pass may surface rationale for design choices (sandbox-relative paths, bounded raw recall) not visible from commit messages alone.
