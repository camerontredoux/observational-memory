# om_recall ranking: BM25-lite inside the whole-term gate (issue #20)

Scored with no model, on saved transcripts. Each query runs over its transcript as it stood when the query was made.

## What was compared

- **Current**: `om_recall`'s ranking in `hooks/recall.ts`. The whole-term gate keeps the blocks that hold every
  term whole. If no block holds every term, the search is **loose**: it keeps the blocks that hold any term and ranks
  them by IDF-weighted terms first. Then the ranking puts first the most terms whole on one line, then the most terms
  on one line, then the newest.
- **BM25**: the same gate and the same hits, with pi's BM25-lite as the order (k1 = 1.2, b = 0.75, newest on a tie).
  On a query of 2 or more terms, hits under 20% of the top score are dropped. At most 50 hits are kept. The compound
  handling stays: `101` inside `101047290` does not match `shard-101`. A compound term held only by its parts counts
  the frequency of its rarest part.

`tests/eval/ranking.ts` holds both rankings. Its copy of the current ranking is checked against `recall()` on every
query: the blocks `recall()` shows are the top of the copy's order on all 98 queries.

Metrics:

- **Rank**: the rank of the first needed block among the hits. `-` means no needed block passed the gate.
- **Size**: the number of hits. `om_recall` shows at most 20 of them (and at most 10,000 characters), so a smaller
  size changes the "N match(es)" count and the "more matches not shown" line, not the context cost.

- **Benchmark**: every `om_recall` search in the live runs. They are 3 distinct queries: `shard-101`,
  `shard-101 checksum` and `test_request_id_header assert`.
- **Replay question sessions**: every `om_recall` search that a Sonnet question session made about a real
  transcript (`/tmp/om-replay/*/*/results.jsonl`). Each query is given to the fact question (one with `expect` and no
  `to`) that shares the most words with it. 24 queries share no word with any fact question, or tie two, and are left
  out. Most of these target handoff questions, whose `expect` words are too common to find one block.
- **Private**: the sessions over firstmate-11 and the chain that holds it. Only their totals are given here. The
  script prints their queries only with `--private`.
- **Synthetic**: queries written from each scenario's continuation prompt. No model made them. They run over the
  newest om+recall run of the scenario, cut after the continuation prompt.
- The `om_recall` calls in this repository's own sessions are not used: nothing records which block each one needed.

- **Every term whole** (the usual case): BM25 is worse. The current order puts first the block with the most query
  terms on one line. That is the block that states the fact. BM25 prefers short blocks and repeated terms. In 8 of the
  10 losses the needed block moved from rank 1 to rank 2 or 3.
- **Loose**: BM25 is slightly better (4 better, 2 worse). This is 19 queries, 18 of them private.
- **The noise floor** never dropped a needed block. It shrank the size of 7 of the 71 whole-gate queries, by 1 or 2
  hits.
- **The cap of 50** cut all 19 loose queries, from a median of 858 hits to 50. The display already shows at most
  20, so only the count in the header changes.

## Limits

- **Sample**: 90 real queries, 63 distinct, but only 10 distinct on public transcripts. 66 of the 90 are Sonnet's
  searches in replay question sessions, not in working sessions. The benchmark adds 17 queries that both rankings
  rank the same (3 distinct queries in small synthetic transcripts).
- **Repeats**: the replay sessions ask the same questions at several boundaries and in several runs, so similar
  queries repeat. The worse and better counts are close to their distinct-query counts (10 and 6).
- **Loose needed blocks**: a question's `expect` strings can be common words (`first`, `worktrees`), so a query can
  have many needed blocks (up to 538). Rank is then the rank of the first of them, which flatters both rankings the
  same way. On the 30 queries with 5 or fewer needed blocks, the two rankings tie on every query.
- **Attribution**: each query is given to the question it shares the most words with. A query that tried a different
  angle on the same question is still scored against that question's `expect`.
- Rank is not the same as success. A model reads the excerpts of up to 20 hits, and 86 of the 90 needed blocks are
  in the current top 20.

## Recommendation

Keep the current ranking. Keep BM25 rejected. BM25 moves the needed block down more often than up (12 against 7), and
at rank 1 it is worse (70 against 75). The issue's rule was to adopt BM25 only if it ranks the needed block higher
with no loss elsewhere. It does not meet that rule. The noise floor and the cap cost nothing in rank on this set, but
they only change the match count, which `om_recall` already caps at 20 shown hits. BM25's one gain is in loose
searches (4 better, 2 worse on 19 queries). That is too few queries to change the order of loose searches alone.

## How to rerun

```sh
bun scripts/bench-bm25.ts             # the table and the totals; private queries hidden
bun scripts/bench-bm25.ts --private   # with the private queries, for local review only
bun scripts/bench-bm25.ts --json FILE # every row as JSON (private queries hidden unless --private)
```

It reads the transcripts that `docs/bench/*.jsonl` names, `/tmp/om-replay/*/*/results.jsonl` with their sessions
under `~/.claude/projects`, the replay specs, and the main checkout's `tests/fixtures/*.replay.local.ts`. It makes no
model calls.
