# v1.3.0 on the real-transcript replays, 2026-09-24

> **Correction (later the same day):** the om+recall drop below (handoff 29 → 26/44, om-v04 facts 26 → 19/27) came from the harness, not the plugin. This run asked fact and handoff questions in one session, and scored only a +recall session's last reply. Asked as v1.2.0 was, v1.3.0 scored 28/44 with 17 `om_recall` calls. om-v04's fact drop was Observer variance: two more runs scored 25 and 26 of 27 for om. See the last section of `README.md`.

v1.3.0 (`a0f3404`, issues #14 and #15) changed the Reflector and the handoff:

- The Reflector keeps the newest ~12k tokens of observations unchanged, aims for 60–90% of its 20k target, and
  rejects a result under 40%. 🔴 lines pass through by code.
- A standing compaction note sits in the system prompt.
- The `<continuation>` record has "Next steps", "Told the user", and a git environment block.
- An oversized first message keeps its head and its tail.

This report compares v1.3.0 with v1.2.0 on the three single-transcript replays and the four-session chain from
`2026-09-24-reflector.md`. Both versions ran with the real Observer and Reflector (pi, Luna). The chain and
firstmate-11 include private transcripts, so only aggregate numbers are given for them.

```
bun scripts/bench-replay.ts om --transcript <name> --pi live --out /tmp/om-replay/<name>/om-v130
bun scripts/bench-replay.ts report --transcripts <name> --om-run om-v130
bun scripts/bench-replay.ts reflections --transcript <chain> --run /tmp/om-replay/<chain>/om-v130
bun scripts/bench-replay.ts questions --transcript <name> --configs om,om+recall --om-run om-v130 --budget-usd N --live --out <dir>
```

## The new handoff questions

The earlier questions ask about facts "from boundary n onward". The handoff is about one boundary, so each
committed spec now has boundary-specific questions (`Question.to`). The same questions went into firstmate-11's local
spec:

- `next-N`: "What was the assistant about to do next when this context begins?" The expected words come from what
  the assistant actually did in the rows just after cut N.
- `told-N`: "What had the assistant most recently reported to the user?" The expected words come from the
  assistant's last message to the user before cut N.

| transcript | handoff questions | boundaries |
|---|---:|---:|
| om-orchestration | 10 | 5 |
| om-v04 | 17 | 9 |
| firstmate-11 | 17 | 11 |

The check is strict. Each answer must contain every expected whole word. An answer that names the right task in
other words fails. Every configuration uses the same check, so compare the scores with each other, not with 100%.

The v1.3.0 chain reflected once, after boundary 19. v1.2.0 reflected after boundary 22.

| level, Reflector calls | 1, 1 call | 1, 1 call, $0.013 |

The memory then grew from ~16k back to ~38.7k tokens by boundary 31, just under the 40k threshold, so no second
reflection happened. The chain ends one or two compactions before it would.

## Verdict against issue #14's acceptance

- Lands within about 50–100% of the target: **met**, 81%.
- Identifiers the next boundaries need survive: **met**, 8/8 (v1.2.0: 1/10).
- om alone answers the dropped-identifier questions after the reflection about as well as before: **met, with a
  caveat**. om alone scored 3/5 at every post-reflection boundary (v1.2.0: 2, 0 and 1 of 5). Every fact question stayed exact on both sides of it.
- Every 🔴 line unchanged, none added: **met**, 10 → 10 identical, 0 promoted.
- Constraints 100% held: **met**, 18/18 across the reflection and 446/446 over the chain.
- A second reflection: **did not happen**. The memory reached ~38.7k of 40k by boundary 31, the end of the chain.
- No regression on the three single-transcript replays: **mixed**. Constraints held everywhere, and the fact
  questions held on om-orchestration and firstmate-11. om-v04 lost identifiers (66% → 56%) and fact answers
  (25/27 → 23/27, om+recall 26/27 → 19/27). No reflection runs in those replays, so the cause is outside the
  Reflector. The `recall-required` live scenario was not re-run, because it needs a herdr pane and this run used
  none.

## Limits

- One run per version. The Observer is a live model, so the identifier retention of two runs of the same build
  can differ by several points.
- The handoff check wants exact words, so it undercounts right answers in other words, the same way for every
  configuration.
- The v1.3.0 sessions asked fact and handoff questions together; the v1.2.0 handoff sessions asked handoff
  questions alone. That changes how often the model called `om_recall`.
- The built-in configurations have recorded chains for om-orchestration only.
