# Compaction ideas from other systems

Proposals X1 to X5 for `compaction-ideas.md`, from bounded web research (12 searches and fetches) on how other agents and memory systems compact context. Best first. The baseline figures are from HEAD af0940d on the hardened bench: main 74.8; mean context about 22k tokens, of which the raw tail is about 10.9k and the observations about 7.5k.

### X1 tail-mask: mask old tool results in the raw tail. proposed
- **Idea:** (incremental) In the raw tail that compaction keeps, replace each successful tool result that is older than the newest 3 tool uses and longer than about 500 characters with its first line or two (about 200 characters) and the existing `omissionMarker(…, 'result')`. Keep the tool call, every error result and all assistant and user text whole. This is observation masking, the cheapest step that every surveyed system takes before summarizing, or instead of it.
- **Evidence:** The raw tail is the biggest part of the context: about 10.9k of 22k at HEAD, and the tokens gate passes 1/25 cuts. Tool results are 56% of a coding agent's context (CliffCompaction). JetBrains found that masking old observations halves cost and matches or beats LLM summarization in solve rate on SWE-bench Verified. Anthropic's `clear_tool_uses_20250919` does this server-side: by default it keeps 3 tool uses and puts a placeholder in place of each cleared result. OpenCode prunes tool outputs beyond its newest 40k protected tokens once 20k or more can be pruned. CliffCompaction drops results over 500 characters, keeps tool calls as signatures, and on Terminal-Bench beats Claude Code's summarization at the same 45k budget (76.7% against 71.0%). This is the goals doc's "keep less in context, make what's kept point to what's stored": om_recall already recovers a cut result.
- **Change:** `hooks/register.ts`, where the compaction returns the rows from the cut on: rewrite `toolResults` text as described, with new constants such as `TAIL_KEEP_TOOL_USES = 3` and `TAIL_MASK_CHARS = 500`. First check how the next compaction's `persistent` test (line 1348) sees a masked row. If `$.session.messages()` returns the masked copy, the hashes match. If it returns the original, hash a masked row by its unmasked form (the marker makes it recognizable) or record its original hash in the marks.
- **Test tier:** cheap first, then full, because it changes every compaction.
- **Expected:** Raw tail about 10.9k down to about 6–7k. Context about 21k down to about 17k (−20%), and the ratio about 13% down to about 11%. The tokens gate goes up. No model tokens are added.
- **Risk:** The bench reads a raw-tail row whole only when it is the transcript's own row (`proseContext`). A masked row becomes prose-only, so the identifiers and facts gates may drop partly as a grading artifact. Phase2 should check the lost items by hand before rejecting the idea. The bench can't see the behaviour cost: the model may re-read files or re-run commands whose output was masked (trajectory elongation). Keeping the newest 3 results and all errors limits this.
- **Result:**

### X2 open-failures: a code-built list of failures still open, in prose. proposed
- **Idea:** (incremental) Every memory message carries a short, model-free section of the tool failures that still matter: each failure that no later call of the same command or file fixed, and each policy block (a hook block, a missing tool). Each is one prose sentence with its time, tool, target and first error line verbatim. The list carries across compactions, and code removes an entry when a later call of the same target succeeds.
- **Evidence:** failures is 36.4 on main and 25.7 on the chain, the weakest mechanical gate. Claude Code's own compaction prompt has an "Errors and fixes" section, and Factory's persistent summary keeps "breadcrumbs" so the agent can find truncated outputs again. Research on compression costs names repeated mistakes and redundant tool calls as the damage that pass/fail metrics miss (arXiv 2608.16370). The logic already exists: `extractOutstanding` in `hooks/vcc.ts` finds unfixed failures. But it runs only inside the brief, it looks at the newest `OUTSTANDING_TAIL` blocks only, it is replaced at every compaction, and its `- HH:MM` list lines are not prose. The always-on brief was rejected because the old live benchmark showed no gain at its 6/6 ceiling. That benchmark had no failures gate.
- **Change:** `hooks/vcc.ts`: export a failure scan over the rows a compaction removes from context, including policy blocks even when a later call works around them. `hooks/register.ts`: keep the open list in the memory message and parse it back like the continuation record. Render it as sentences, for example "At 14:32 the Bash command `bun test tests/replay.test.ts` failed with `…`; no later run of it succeeded", inside `<continuation>` under a code-read header like the git environment's. Cap it at 8 entries or about 500 tokens, newest kept. `hooks/prompts.ts`: add the header text.
- **Test tier:** cheap, then the chain, where failures is weakest.
- **Expected:** failures 36 up to about 70–85, worth +1.5 to +2.5 on the total. Up to about 500 tokens per context. No model tokens are added.
- **Risk:** The gate picks failures with nearly the same rule (unresolved, recurring or policy), so part of the gain comes from the design matching the rubric. Judge the idea by whether the sentences read as useful and, if possible, by a `--behavior` probe such as "May you run X again as is?". A failure fixed in a way the scan can't see (a different command) stays listed and could make the model too cautious. The cap and the "found by code" header limit this.

### X3 supersede: link a new observation to the older one it replaces. proposed
- **Idea:** (incremental) Show the Observer the few older observation lines that share a whole identifier with its chunk (a path, a constant, a port, a flag, a branch), each with its id. When a new line gives a newer value or state of the same thing, the Observer ends it with `(supersedes o123)`. Code then leaves the superseded line out of the rendered memory. The line stays in the ledger, and om_recall still finds its source. This extends the existing `(replaces <id>)` chain for constraints to 🟡, 🟢 and ✅ lines.
- **Evidence:** "Superseded value, latest wins" is item type 1 in `docs/research/hard-compaction-items.md` (MemFail), and file-state (59.5) is the same problem for files. Zep/Graphiti never overwrites a fact: when a new episode contradicts an edge, it closes the old edge's valid-time window. Mem0's update phase compares each new fact with similar stored ones and chooses ADD, UPDATE, DELETE or NOOP. Mastra's own Reflector removes observations that have been superseded. Our Observer is a pure mapper that never sees older lines. The Reflector only runs at 40k, which never happens on the main corpus, so a stale value stays beside the new one as a near-miss distractor (Chroma).
- **Change:** `hooks/register.ts`: in `beforeRows` or next to it, select up to about 1k tokens of committed entries whose whole-term identifiers overlap the chunk's, newest first, and pass them between PRIOR markers as inert data, as CONSTRAINTS are passed now. Parse `(supersedes oN)` like `(replaces …)`, refuse it for 🔴 lines and for ids not shown, and skip superseded entries when rendering and in the Reflector's input. `hooks/prompts.ts`: add one paragraph on when a line supersedes another (the same thing, a newer value or state; never only a related one).
- **Test tier:** full with `--samples 2` or more. Every Observer input changes, so every reply is a new draw, and `om-direction.md` asks for 3 or more runs per arm before a gain counts.
- **Expected:** Gains on latest-wins, reversal and file-state items, and on near-miss distractors. Observations get slightly smaller as stale lines drop out. Observer input tokens rise about 5–10% (up to 1k on a 10k chunk). Output tokens stay about the same.
- **Risk:** A wrong link hides a live fact (for example, two services with different ports). Allowing links only to lines that share an identifier and were shown to the Observer limits this, and the ledger keeps the line. The rejected whole-conversation Observer (2.6–3× cost, no gain) is a warning. This idea differs because it adds a small targeted list rather than the history, so prompt caching doesn't matter. Watch for the Observer re-observing the prior lines. They are inert data, and the prompt must say so.
- **Result:**

### X4 contrast: learn Observer guidelines from items it loses. proposed
- **Idea:** (incremental, a method) Run one round of ACON's guideline optimization. Take the hard items that the transcript holds but the compacted context loses, and pair each with its source span and the Observer's lines for that chunk. A strong model, offline, writes why the notes lost it, and then proposes at most 5 guideline sentences for the Observer prompt. Phase2 A/Bs each sentence alone.
- **Evidence:** ACON refines a natural-language compression guideline from paired cases where the agent succeeds with the full context and fails with the compressed one. It cut peak tokens by 26–54% with better accuracy, with no model training, and then distilled the compressor into smaller models (our case: Luna). The phase2 notes already list 24 hard lessons, rationale, multi-hop and file-state items that are never captured and 17 that are captured and then lost. Those are ready-made contrast pairs. This complements the prompt-edit ideas: it produces candidate sentences from evidence rather than from reading the prompt.
- **Change:** No plugin change until a sentence wins. Phase2 writes a small throwaway script in `$CLAUDE_JOB_DIR/tmp` that dumps the pairs from a bench `--json` run and the cached Observer replies. One offline model call per batch proposes the guidelines. A winning sentence goes into `OBSERVER_SYSTEM_PROMPT` in `hooks/prompts.ts`.
- **Test tier:** full. Learn from the main corpus only and require the holdout to agree (`--samples 2`), because tuning on 3 transcripts overfits easily.
- **Expected:** Targets rationale (38), lessons (45) and multi-hop (36), the three biggest weighted gaps. The prompt grows by about 100–200 tokens, which each Observer call pays once in its input (about +2%).
- **Risk:** Overfitting to the corpus's wording. The holdout gate is the guard. The offline proposal call costs money, so the coordinator must approve it. A sentence that asks for more detail makes the notes longer: check the efficiency table.

### X5 cliff: model-free compaction as a control arm. parked
- **Idea:** (redesign) A compaction with no Observer or Reflector. It keeps the code-kept tiers (constraints, verbatim user messages, the continuation's environment and latest request, X2's failures) and the code brief over the removed rows, with tool results dropped, tool calls as signatures and assistant text cut to 300 characters. It then discards the previous brief instead of nesting it, and om_recall covers the rest.
- **Evidence:** CliffCompaction does exactly this, verbatim fragments with no summarization. At a 16K threshold it beat full context on Terminal-Bench 2.0 (61.4% against 59.2%) at half the cost. It attributes summarization's loss to summary-of-summary "context drift", which is the same concern as our untested reflection levels 2–4. JetBrains reports that plain masking matches LLM summarization.
- **Change:** `hooks/register.ts`: an `OM_MODE=cliff` switch that skips scheduling and running the Observer and builds the memory from the code tiers and `hooks/vcc.ts`'s brief, with the brief's ranked transcript limited to the removed span. `OM_BRIEF=always`, which compiled the brief at every compaction, was removed (rejected in `docs/plans/om-direction.md`: no measured gain), so the cliff arm needs a switch of its own.
- **Test tier:** full, as a separate arm against the current best.
- **Expected:** Zero Observer and Reflector tokens and no critical-path calls. Quality will likely fall on handoff (the Observer's Next steps and Told the user), rationale and lessons, which only a model writes down. That measures how many quality points per model token the Observer buys.
- **Risk:** Parked because incremental work still pays off (goals: "don't redesign while incremental changes still pay off"). It is cheap to build, though, because the brief and code tiers exist. If phase2 needs a lower bound to show a plateau, run it early. Its brief lines are mostly lists, which `proseContext` doesn't count, so its score would understate what a reader gets from them.
