# Compaction ideas for long-lived sessions

Proposals L1 to L6 for `compaction-ideas.md`, for sessions that run for days or weeks and compact many times in a row. Best first. They come from bounded research (about 20 searches, fetches and source reads) and from reading `hooks/register.ts`. Nothing here repeats I1 to I26, X1 to X5, E1 to E5 or O1 to O5. Where an idea builds on one of those, the entry says so.

The research asked one question: what goes wrong at the 20th, 50th or 100th compaction that does not go wrong at the 3rd? The benchmark's longest track is the four-session chain, which reflects once (twice at r28). Most of what follows only shows beyond that.

## What each system does over many compactions

- **Mastra observational memory** ([source](https://github.com/mastra-ai/mastra/tree/main/packages/memory/src/processors/observational-memory), [docs](https://mastra.ai/docs/memory/observational-memory)). The observation log "stays around 40k tokens, however long the conversation runs": reflection starts in the background at 50% of its threshold and falls back to a synchronous run above 1.2x. Each reflection writes a new *generation* record, and older generations stay in storage. Observation groups keep their raw message ranges through reflection, so the `recall` tool (retrieval mode, optionally vector-indexed at buffer time) can reach the source. The Reflector condenses the oldest observations hardest and drops superseded ones.
- **Mastra Subconscious** (experimental, same source, `subconscious/`). Three background agents over the observations. *curate* keeps durable knowledge records and soft-deletes superseded ones. *pins* are a bounded always-in-context set (default 20 pins, 2,000 characters): "Unpin an entry as soon as it stops being unconditionally true", and pin only what a future agent "would not think to search for". *remind* takes up to 12 terms from new observations, searches the knowledge store, drops the thread's own records from the last 30 minutes, and sends a grounded reminder, or stays silent.
- **OpenAI Codex CLI** ([compact.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs)). The new context is the newest user messages up to 20k tokens, plus one summary. Earlier summaries are left out of the user-message list, and the old summary is part of the history that the next summary is written from, so it is summary of a summary. A newer "token-budget" mode skips the summary and starts a fresh window with the initial context only. The open issues show the long-session failures: 74 compactions in 5.9 h with 95% followed by re-reading a file or re-running a test ([#36664](https://github.com/openai/codex/issues/36664)); a handled steer re-acknowledged as new after a later compaction ([#32627](https://github.com/openai/codex/issues/32627)); progress jumping from 97% back to 42% ([#25792](https://github.com/openai/codex/issues/25792)).
- **Anthropic Claude API compaction** ([docs](https://platform.claude.com/docs/en/build-with-claude/compaction-on-demand)). "Compact again": the new block "summarizes the old summary and everything after it". System messages inside the summarized range "stop applying once the block replaces them", so an instruction that still matters must be restated in a standing message. The [long-running harness post](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) keeps state outside the context instead: `claude-progress.txt`, a `feature_list.json` where every feature starts `"passes": false`, and the git log, read at the start of each window. That stops premature "done" claims.
- **OpenCode** ([compaction.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/session/compaction.ts)). An anchored, iterative summary with fixed sections (Objective, Important Details, Completed, Active, Blocked, Next Move, Relevant Files). The update prompt says: "Carry forward objectives, constraints, user directives, decisions, and parallel workstreams from the <prior-summary> even when the <conversation> does not mention them. Drop only what is finished and no longer needed." Old tool output is pruned past a 40k protected window.
- **Letta context repositories / MemFS** ([post](https://www.letta.com/blog/context-repositories/), [docs](https://docs.letta.com/letta-code/memfs)). Git-backed memory files. Files in `system/` are always loaded. The rest of the file tree is visible, and each file loads on demand ("progressive disclosure"). A sleep-time agent writes memory in the background. A "defragmentation" subagent reorganizes the files into "15–25 focused files" when memory gets messy.
- **Research: the compaction cliff** ([arXiv 2608.22752](https://arxiv.org/html/2608.22752v1)). Under production "keep every safety rule" prompts, constraint preservation falls from 53% after one compaction round to 10% by round five. Their fix is type-aware routing: constraints and procedures are pinned unchanged, and the rest is compressed. A post-compaction verifier escalates when the budget cannot hold every critical item, instead of dropping some silently.

Looked at briefly or not at all, within the budget: Cline/Roo condense, Goose, Aider, Amp threads. None had a long-session mechanism that the systems above don't already cover.

## What long sessions need from the benchmark

Two gaps apply to several entries below. They are named once here.

- **A long chain.** `chainTranscripts` joins 4 transcripts 1 h apart. A track of 10 to 15 corpus transcripts with day-long gaps (`gapMs` 24 h), graded only at every 5th cut to keep it cheap, would run 3 or more reflections, grow the pinned tier and cross day boundaries. L1, L2 and L4 can only be measured end to end there. It is a paid `--record` build once, then exact replays.
- **Recall-aware credit.** The rubric grades what the context says. An idea that moves a fact out of context and leaves a pointer (L1's index, L2's episode lines) always scores as a loss, even when `om_recall` would find it in one call. A "pointed" credit would fix this: an item partly passes when the context holds a line whose source range covers the item's evidence and whose words, used as an `om_recall` query, rank that evidence first. This check is code-only.

## Proposals

### L1 pin-lifecycle: keep the pinned tier bounded, and overflow it to an index instead of falling off a cliff. proposed
- **Idea:** The pinned tier (the `<corrections>` and every 🔴 line in the observations) only grows today. A constraint leaves it only when a newer one says "(replaces <id>)". Give it a lifecycle in two steps.
  1. *Overflow, not fallback (code, exact).* When the pinned tier passes its cap, render the newest pinned lines whole, and the oldest as index lines instead: `* 🔴 2026-09-12 14:50 "Use pnpm here…" (older constraint, shortened; om_recall "Use pnpm here" for its full text)`. The ledger keeps every line whole, and the Observer's CONSTRAINTS list stays whole, so Observer inputs don't change.
  2. *Scope (Observer, `--record`).* The Observer marks each correction as standing (a rule or preference for the session or repo: "always", "never", "don't") or scoped to a named task. A scoped constraint moves to the index once its task has been in Completed for 2 compactions. A standing one never moves while the tier fits its cap.
- **Sources:** the compaction-cliff paper (pin constraints by type; escalate rather than drop when the budget cannot hold them); Mastra pins (a hard pin budget; "unpin as soon as it stops being unconditionally true"); Anthropic compaction docs (instructions inside the summarized range stop applying unless restated in a standing place).
- **Why it matters for long sessions:** Two cliffs exist in the code today, and only a long session reaches them.
  - `CONSTRAINTS_MAX_TOKENS = 8_000`: over it, `build` throws `OVER_CAP`, and **the built-in compaction runs instead** (`register.ts` ~1444). That is a blocking model call that also discards every guarantee the plugin gives, the verbatim constraints included.
  - The Reflector's target is `REFLECT_TARGET_TOKENS − (🔴 lines + kept recent notes)`. The kept notes are about 12k, so once the 🔴 lines in the observations pass about 7k, `target < 1_000` throws and no reflection can run again. The observations then grow until the budget floor or the fallback.
  The chain carries about 1.5k of constraints per cut after four sessions. A week of firstmate-style work, with many "don't do X in this PR" decisions, reaches either cliff.
- **Expected:** Quality stays the same until the cap and holds after it, where today it collapses to the built-in summary. Late-session context shrinks by the index savings (a shortened line is about 25 tokens against about 60 to 150 for a whole line). Step 1 adds no model tokens. Step 2 adds about 5 output tokens per correction. No latency, and one less path into a blocking built-in compaction.
- **Change:** `hooks/register.ts`: in `build`, replace the `OVER_CAP` throw with the overflow render. In `maybeReflect`, count only the whole-rendered 🔴 lines against the target. `hooks/prompts.ts`: one Observer sentence for the scope tag, and `MEMORY_INSTRUCTIONS` saying what a shortened constraint is.
- **Test:** Step 1 is cheap and exact. Replay the chain with the cap lowered to 1k, as a stand-in for a week of growth. Standing constraints must stay 100% on the constraints gate. Compare the lowered-cap run with and without the overflow (without it, it falls back). Step 2 is `--record --samples 2`, full. It needs the **long chain** to show the cliff without the lowered cap.
- **Risks:** Weakens the proven guarantee that every constraint is shown verbatim. Mitigate it: standing constraints are never shortened while they fit, and a shortened one keeps its first words and its time. A wrong "scoped" tag hides a standing rule; the index line and `om_recall` still hold it. Adds a new parsed format.

### L2 episode-index: bound the reflected tier with model-free episode lines. proposed
- **Idea:** A four-level memory where no fact is re-encoded by a model more than twice. Hot: the raw tail. Warm: Observer notes. Cool: reflected lines. Cold: episode lines, with the transcript as the frozen store. With I25, reflected lines pass through later reflections unchanged, and that tier grows about 3k per reflection with no bound (I25's own risk). When the reflected tier passes a cap (for example 6k), the next reflection also turns the oldest reflected lines into **episode lines**, one per stretch of work with one goal: `* 📁 2026-09-12 09:10 to 17:40 <goal, outcome, the key decision and why> (source A to B)`. After that, no model rewrites an episode line. When the episode tier passes its own cap (for example 3k), code shortens the oldest episode lines to their date range, first 12 words and source range. It never summarizes them again.
- **Sources:** the compaction-cliff paper (retention decays with each re-encoding: 53% to 10% over 5 rounds); Claude API "compact again" and Codex (summary of a summary, the pattern to avoid); Letta (an always-visible tree over on-demand content: progressive disclosure); Mastra (the log stays near 40k however long the session runs; groups keep their raw ranges through reflection, so recall reaches the source).
- **Why it matters for long sessions:** It is the missing bound. After I25, every tier except the reflected one is capped: the tail by the budget, notes by reflection, user messages at 10k and the pinned tier by L1. It turns "the context grows until something breaks" into a fixed size (about 12k notes + 6k reflected + 3k episodes), with drift capped at two model rewrites per fact.
- **Expected:** On sessions past 3 reflections, the context stays flat instead of growing about 3k per reflection. Quality on old detail goes down in the context and up through recall. The rubric can only see this with recall-aware credit. Reflector tokens go down, because reflected lines are never resent. No extra calls: episode lines come from the same Reflector call. No critical-path change.
- **Change:** `hooks/register.ts`: an entry kind for episode lines (on top of I25's `r: true`), the two caps in `maybeReflect` and a code shortener. `hooks/prompts.ts`: the Reflector's episode instructions. Consider it the in-context face of #21 (I6): #21 files condensed notes by topic, and L2 keeps a dated index to them.
- **Test:** A Reflector change: chain `--record --samples 2`. The current chain never reaches the episode cap, so this needs the **long chain** and **recall-aware credit**. Without both, it can't be measured. Test it only after I25's result.
- **Risks:** An episode line is a third encoding for the facts it keeps. The model-free shortening below it stops a fourth. A wrong episode boundary merges two goals. Old detail becomes recall-only, so behaviour depends on the model calling `om_recall` (1 call per run today, 6/6 success).

### L3 remind: surface old memory that matches the current work, by code, at compaction. proposed
- **Idea:** At compaction, code takes up to 12 salient whole terms (paths, identifiers, constants, command names) from the raw tail and the continuation's Active and Next steps. It searches the history that is no longer in context with `om_recall`'s whole-term ranking: ledger entries that are no longer rendered, older memory messages in the transcript, and user messages the 10k cap dropped. It drops hits already in the context, and adds at most 5 lines, about 300 tokens, under a header like "Earlier in this session, possibly relevant (older; newer lines win)". Each line keeps its time and source range. If nothing shares 2 or more whole terms with the tail, it adds nothing.
- **Sources:** Mastra Subconscious `remind` (`findReminderSources`: 12 terms, stop words, 5 results per term, 10 in total, the thread's own fresh records dropped, silence when nothing is relevant); Mastra's pin rule (in-context memory is for what the agent "would not think to search for"); Mastra retrieval mode (groups indexed at buffer time, raw ranges kept).
- **Why it matters for long sessions:** After a week, almost all history is out of context, and `om_recall` only helps when the model knows what to ask. When the work comes back to a file or a subsystem days later, the decision or failure from last time is the thing it doesn't know exists. The main corpus has little out-of-context history, so the benefit grows with session length.
- **Expected:** Up on multi-hop, rationale and failures items whose evidence left the context, on the chain and more on a long chain. Context up to +300 tokens, and often 0. No model tokens. Latency is a local search at compaction (milliseconds; the transcript is already loaded for the brief's references).
- **Change:** `hooks/register.ts`: at build time, a `reminders(tail, continuation, cold)` step reusing `recall.ts`'s whole-term scorer through `RecallIo`. Render only: keep reminder lines out of the ledger and out of the Observer's input, so later Observer inputs don't change. Check first whether `om_recall` already indexes earlier memory messages in the transcript. If it does, the cold corpus is free.
- **Test:** Cheap and exact, on the chain (the main corpus has too little cold history to show anything). Check the holdout for rubric-matching: the terms come from the tail, and rubric items are about the tail's topic, so part of a gain may be matching the rubric.
- **Risks:** Near-miss distractors, and stale values surfacing beside newer ones. Mitigate it: skip superseded lines (X3/I11) and lines a newer 🔴 replaced, require 2 or more shared whole terms, and label the lines as older. The model may treat a reminder as an instruction. The header frames the lines as data.

### L4 threads: carry every open line of work, and let untouched ones go dormant. proposed
- **Idea:** The continuation record gains a bounded `Threads:` field, one line per open thread of work: its goal in a few words, its status, when it was last touched, and its source range. The Observer carries forward each thread the chunk does not mention, as the record already does for Waiting and Blocked. Code applies the aging: a thread untouched for 3 compactions or 24 h becomes one short dormant line. A closed thread shows once in Completed and then drops. Cap it at 8 lines, about 400 tokens.
- **Sources:** OpenCode's update prompt ("carry forward … parallel workstreams … even when the conversation does not mention them. Drop only what is finished"); Anthropic's long-running harness (`feature_list.json` with `passes` flags, so done work isn't reopened and open work isn't declared done); Codex #25792 (progress regressing after compaction) and the ExecPlan answer in that thread.
- **Why it matters for long sessions:** `Active:` follows the newest thread, and I26 adds the umbrella goal. Neither keeps the third or fourth open line of work: a PR waiting for review, a lane that is paused, a bug parked for later. Over days, those drop out of the record after one chunk that doesn't mention them, and then exist only in the observations, where reflection condenses them. This coordinator session, with 5 lanes, is the case.
- **Expected:** Up on handoff and multi-hop items about paused work. Context +200 to 400 tokens. Observer output about +40 tokens per call (+5%). No extra calls.
- **Change:** `hooks/prompts.ts`: the field and its carry-forward rule. `hooks/register.ts`: parse it like the other fields, and apply the aging and the cap in code (the Observer gives the time it was last touched; code compares it with the compaction count). Build it together with I26 (the session line) as one prompt change, and with I7 when the session uses tasks.
- **Test:** `--record --samples 2`, full. The rubric has no thread gate. Add 1 or 2 items per chain member ("what is still open from member 1?"), and a `--behavior` probe "list the open lines of work". The chain's 4 unrelated sessions are a natural test: once member 2 starts, member 1's open work should be dormant, not Active and not gone. The aging only shows on the **long chain**.
- **Risks:** Threads the user abandoned without saying so stay listed; the dormancy rule limits that. A longer record for the Observer to rewrite each chunk. Overlap with I26: land them together.

### L5 working-set: tell the model which files and test runs it has already seen, and whether they changed since. proposed
- **Idea:** A code-built section in the continuation, beside the git environment: the files read or edited since the last compaction or two, newest first, each with when it was last read or edited and whether it changed since. Code checks the file's mtime and size at compaction, reusing the environment's git read. Also the last run of each test command: pass or fail, and when. Cap it at 15 files and 5 commands, about 300 tokens. Each entry says that `om_recall` returns the last read of an unchanged file, so the model doesn't need to read it again.
- **Sources:** Codex #36664: 74 compactions in 5.9 h, 70 of them (95%) followed within 2 minutes by re-reading a file or re-running a test already run. One file was read 25 times. 89.8% of the session's content was tool output. JetBrains and CliffCompaction (in `outside.md`) warn that masking lengthens trajectories.
- **Why it matters for long sessions:** A re-read costs tokens once per compaction, and a long session compacts many times, so the cost adds up. I9's tail mask (older results over 250 tokens cut) makes re-reads more likely. This gives the model the facts to skip a re-read safely: "unchanged since you read it at 14:02" or "edited since".
- **Expected:** The file-state gate (58.9) may go up. Context +300 tokens. No model tokens. Local `stat` calls at compaction. The main benefit, fewer re-reads after compaction, is invisible to `bench-compact`.
- **Change:** `hooks/register.ts`: collect Read, Edit and Write paths and test-command results from the rows, `stat` them next to `GIT_TIMEOUT_MS`'s git read, and render them under a code-read header. `hooks/prompts.ts`: the header text.
- **Test:** Cheap and exact for the context and the file-state gate. First, measure the problem on our own corpus with no model: count how often, after each compaction in the real transcripts, the model re-read a file within 5 turns that was unchanged since its last read. If that rate is low, drop the idea. If it is high, a `bench-live` run counting re-reads per compaction is the real test.
- **Risks:** A file changed outside the session with the same size and mtime (rare). More list-shaped context, which `proseContext` doesn't credit; write each entry as a sentence. Overlaps X2 (open failures) on test results: share the scan.

### L6 handled: mark each quoted user message as answered or open. proposed
- **Idea:** In `<all-user-messages>` and in the latest-request quote, code adds each message's status, found from the rows: "(answered 14:32)" when an assistant turn ended after it with a text reply and no newer user message, and "(open)" when the turn was cut off or is still running. The continuation's Completed stays the Observer's view. This adds a code fact next to it.
- **Sources:** Codex #32627 (and the older #27894 it points to): "a steering message can be handled once, then treated as newly relevant again after a later automatic compaction"; 82 root tasks in one user's 3,125 rollouts had a steer before a later compaction. Codex #25792 (reopened work after compaction).
- **Why it matters for long sessions:** The plugin shows up to 10k tokens of verbatim user messages again at every compaction. The newest one is quoted "not as an instruction to start it again", which is a prompt-level guard. Each compaction is another chance to act on an old request again, so the risk grows with the number of compactions. A code-derived "answered" mark doesn't depend on the Observer.
- **Expected:** Fewer repeated actions. The rubric has no item for this. About 5 tokens per quoted message (under 0.3k). No model tokens or latency.
- **Change:** `hooks/register.ts`: `capUserMessages` and the continuation's latest quote carry a status found from the rows after each prompt. The ledger's prompt entries store it.
- **Test:** Cheap and exact for size (context text only). Quality needs a `--behavior` probe per transcript: "Is the user's latest request still open? Should you start it again?", graded against where each cut falls. The reversals and handoff gates must hold.
- **Risks:** "Answered" isn't "done": a reply may have promised follow-up work. Keep the wording factual ("a reply followed at 14:32") and leave doneness to Completed and Next steps. An interrupted turn misread as answered; treat a turn with no final text as open.
